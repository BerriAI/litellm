## Overview

Ported from BerriAI/litellm-internal-skills. Slash commands this skill mentions but does not define (`/qa-keys`, `!team`, `/concernloop`) live in that repo; when they are not installed, fetch credentials from the team vault by hand and run the repo's review loop directly

Audit a litellm fix end to end before calling it done. The audit answers one question: for every surface the fix can touch, does the real proxy do the right thing under happy, sad, edge and chaos conditions, and is that proven by a deterministic integration test a reviewer can rerun. Every cell of the audit is a `tests/integration/` test: the proxy, Postgres, Redis and every litellm component in the path run for real; the only doubles are at the edges, the upstream provider the proxy calls (`tests/integration/_support/upstream.py`) and the destination a callback posts to (a local sink that speaks the vendor's wire protocol). A row whose behavior only the real third party can prove (a vendor verdict, a real deployment's error shape) gets a live cell in the same audit: same rig, same head, the real vendor reached with a credential fetched through `/qa-keys`, recorded in the same matrix. Nothing in the inventory is deferred to another suite or listed as out of scope. No cell is allowed to be flaky. It runs after the fix exists (unit tests green, PR open or about to open) and produces a pass/fail matrix from two runs, the merge base and the head, plus an updated PR proof section. It is not a substitute for the fix workflow (`!team`), it is the last gate before handoff (`!team` phase 12), and the tests it writes ship in the PR

## What's Needed From User

- The PR URL or branch under audit, plus the ticket id if any
- Which product behavior the fix changes, in one sentence (the audit derives the matrix from this)
- Nothing else. The deterministic cells need no credential; when a row can only be proven against a real third party, fetch that credential from the 1Password `Shared` vault with `/qa-keys` and run the row live in this audit. Only when the vault has no item for it do you ask, and until it is in hand that row is unverified and the verdict is BLOCKED BY HUMAN, never out of scope

## Procedure

1. Pull, check out the PR branch in its own worktree, and read the diff. Write a surface inventory before writing any test: every endpoint the change can affect (at least `/v1/chat/completions`, `/v1/messages`, `/v1/responses` for anything in the request or logging path), streaming and non streaming, sync and async clients (OpenAI SDK, Anthropic SDK, raw httpx), every mode or setting the change branches on (for callbacks: success, failure, success_and_failure, key level, team level, YAML level, explicit disable), and every management endpoint the ticket mentions. Three rows are mandatory whenever the diff qualifies, because each is a path the standard endpoint list does not reach: when the diff reads or writes raw `bytes`, SSE frames or a stream iterator, every pass-through route in the route table (`/v1beta/models/...:streamGenerateContent`, `/bedrock/...`, `/vertex_ai/...`, `/anthropic/...` and siblings) gets its own streaming row, not only the OpenAI-compatible and `/v1/messages` endpoints, because the frames a hook sees on a pass-through route are the provider's own, not the converted ones; when the diff touches a hook, a callback, a metric or a logging payload, every row is duplicated as a response-cache hit (first request populates, second request is served from cache and then goes through the same hook or verdict) because a cache hit skips routing and leaves the attribution fields the sink reads unset; and when the diff adds or changes a regular expression, the worst-case input for that pattern (derived from the pattern itself: the literal a `.*` alternative starts with repeated to the request size limit, nested quantifier fodder, the longest match position pushed to the end) gets a row that times the classifier alone and a concurrent health request, on both legs. When the fix changes an input a whole family receives (the mapping every guardrail hook gets, the kwargs every callback gets, the header dict every pass-through route forwards), list the family from its registry (`guardrail_class_registry`, `CustomLoggerRegistry.CALLBACK_CLASS_STR_TO_CLASS_TYPE`, the pass-through route table) and give every member that builds its output from that input its own row; a grep for the changed key finds only the members that already special-cased it. List the outbound destinations too (provider deployment, guardrail vendor, OTLP, Langfuse), because each one is an edge the audit scripts and whose inbound request the test reads. Write the expected outcome of every row on both legs (merge base and head) into `<scratch>/inventory.md`. Anything not in the inventory is not covered, so be generous
2. Build the rig the way CircleCI does (`tests/integration/README.md`): real Postgres and Redis you own, the owned upstream from `_support/upstream.py` serving the provider responses each cell needs, a local sink per outbound destination that records every inbound request and answers with the vendor's success code, and the proxy from the PR tip on its own port with two workers, `LITELLM_DISABLE_NO_REDIS_WARNING=true`, no `--detailed_debug`, `INTEGRATION_PROXY_URL`, `INTEGRATION_UPSTREAM_URL`, `INTEGRATION_MASTER_KEY` and `DATABASE_URL` pointed at that deployment. Record the exact commit hash the proxy runs. Boot the merge base (`git merge-base origin/main <tip>`) on a second port with the same config for the before leg
3. Happy path matrix: write one test per inventory row under `tests/integration/<domain>/` (the domain a user would name), following `tests/integration/AGENTS.md`: the rates, fixtures and expected values live in the test and are computed by hand, one call, `response.text` in the assert, `eventually(...)` never `sleep`, the node and its `covers` ids registered in `contracts.json`, hard fail never skip. Each test drives the cell through the real client (the OpenAI or Anthropic SDK for the sync and async cells, httpx for the raw cells), consumes the whole stream where it streams, and asserts three things by the response id, never by count: what the caller received, what the upstream received (the upstream exposes actual received requests) and what landed at the destination sink or in Postgres. Score every cell on the whole captured request, not on the field the fix was written for: a cell where the new id resolves and the old id silently stopped resolving is a FAIL
4. Sad paths: every header or body field the fix starts reading sent as an int, a list, an empty string, a 5 KB string, and twice with the same value, plus, for every regex the diff adds or changes, the pattern-derived worst-case string from the step 1 inventory at the largest body the proxy accepts, asserting the classifier's wall time and the `/health/liveliness` latency during it stay within a small multiple of the merge base (a quadratic scan reads as seconds on head and milliseconds on base), on an unauthenticated request, with the spend row or trace it wrote read back; a failing hook or verdict on every path the fix newly routes through it, with the upstream attempt count compared to the before leg; the failure verdict on a multi-item fixture (n>1, multi-part content) wherever the fix now runs a step per item, with the aggregate error or violation output diffed against before; scripted provider errors from the upstream (unknown model, oversized input, 401 on the deployment) in each callback mode, malformed configuration (bad `callback_vars`, unknown callback name, `null` where a list is expected), missing associations (key with no team, team with no settings), a sink answering 403 and 404, and the management endpoint that reports on the feature (`/key/health` and friends). The proxy must not crash, unrelated keys must keep working, and errors must reach the caller in the response body, not just the server log
5. Edge cases: empty versus null versus missing for every setting the fix reads, precedence between key, team and YAML levels, cache expiry of team and key metadata (drive the TTL with the proxy's own settings or invalidate, never wall-clock waits), concurrent updates to the setting while traffic flows, and repeated identical requests to prove idempotent logging (one artifact per request)
6. Chaos, as tests too: stop the destination sink mid burst (20 to 50 concurrent requests across all three endpoints, mixed streaming, all served by the scripted upstream), assert the diagnostics report unhealthy while it is down, restart it, and assert every burst response id lands exactly once. Make the sink answer slowly and assert no deadlock between periodic and explicit flushes and no duplicate uploads. Restart the proxy mid burst and assert the queue drains or document the loss. Kill one worker and assert the other keeps serving. The sink, the upstream and the proxy are processes the test owns, so every outage is scripted and repeatable; the shared box Postgres is never stopped
7. Run the whole selection with `uv run --no-sync python tests/integration/run.py <group>` on both legs. Expected shape: the cells the fix changes are red on the merge base and green on the head; the cells the fix must not touch are green on both. Then run the head selection a second time with the same seeds (`--seed` and `--order-seed` for generative shards): identical collected and passed selections, no skips, no retries. A cell that passes once and fails once is a FAIL to root cause in the product or the test, never a rerun. Live third-party rows are not part of this selection: run each one once per leg from a script under `<scratch>/live/<sha>/` against the same head and merge base proxies with the real vendor configured as the deployment or destination, save the request the vendor received (or the vendor's own record id), the proxy response and the Postgres row as artifacts named by the sha, and record them in the matrix as `live` cells
8. Compare every observation against the outcome contract you wrote in step 1. Any mismatch is a bug to root cause, not noise. If the fix is wrong, fix it on the same branch, push, and rerun every cell plus the chaos step on both legs at the new tip. Never rerun only the failing cell
9. Write the audit report: a matrix with one row per cell (endpoint, mode, client, scenario), the test node id, the response id, the upstream and destination artifacts, base result, head result, PASS or FAIL, and the run's commit hashes. Below it, list every inventory row that is still unverified and why, each one a blocker on PASS. A behavior change the audit observed (a status that now differs, a header no longer forwarded verbatim, an id a caller now controls, a payload a vendor now receives, a value that was stable and is now per-request) is a FAIL row with a decision attached, never a caveat: it ends with the commit that fixed it or the name of the person who approved shipping it and where. A Medium caveat under a passing audit is how such a change ships unnoticed. Link the run manifests and logs
10. Commit the deterministic tests to the PR branch (they ship with the fix; live cells are never committed, they would need a credential in CI), confirm the CircleCI `integration-<suite>` checks are green at that head, and update the PR description's proof section with only this latest audit run (replace stale proof): the matrix, the exact base and head hashes, the two run ids, the test node ids, and for each live cell the vendor reached and the artifact path. Then run the review loop the repo requires (`/concernloop` where it applies), since the audit changed code
11. Decide the verdict from the inventory, not from the rows that ran. PASS requires every row in `<scratch>/inventory.md` to have a cell that was executed live at the head with the expected outcome observed and no mock, patch or stub inside the proxy: a checked-in deterministic cell for a row the scripted edges can prove, a live cell whose artifacts show the real vendor was reached for a row only the third party can prove. Walk the inventory row by row and mark each one VERIFIED (cell ran live, outcome matched, and for a third-party row the artifact names the real vendor, never the scripted upstream) or UNVERIFIED (not run, not written, skipped, deferred to another suite, proven only by a mocked or patched component, or proven only by a curl transcript or unit test); a single UNVERIFIED row blocks PASS. A row the scripted edges can prove gets its cell written and both legs rerun; a row only the real third party can prove gets a live cell run in this audit with the `/qa-keys` credential; a row blocked on a credential the vault lacks or on a decision only a human can make leaves the verdict BLOCKED BY HUMAN with that row named as the blocker; a row that ran and failed makes the verdict FAIL. The unverified list in step 9 exists to make the blocker explicit, not to let the verdict pass around it: a report that lists any unverified row and says PASS is a defect (user ruling 2026-09-22)
12. Hand the report to the user with the verdict first (PASS, FAIL or BLOCKED BY HUMAN), the PR link, the report attached, and every unverified cell on its own line with the reason it blocks PASS

## Specifications

- Every deterministic cell is a checked-in `tests/integration/` test registered in `contracts.json`; a curl transcript, a pytest run of an uncommitted script, or a unit test with a patched component is not a cell. The only other kind of cell is a live cell: a row only the real third party can prove, run through the head and merge base proxies against the real vendor with a `/qa-keys` credential, with the vendor-side artifact saved under `<scratch>/live/<sha>/`. Live cells are not committed, not registered in `contracts.json`, and not part of the CircleCI or twice-run gates; a scripted-upstream run never counts as a live cell
- No component of litellm is mocked, patched or stubbed inside the proxy: no `mock_response`, no patched loggers, no monkeypatched litellm function. Doubles live only at the edges, the scripted upstream and the destination sink, and both speak the real wire protocol
- Deterministic cells call no real provider and need no credential; a row only the real third party can prove is run live in the audit with a `/qa-keys` credential, and no row is deferred to another suite or listed as out of scope
- Every endpoint in the inventory is exercised, streaming and non streaming, sync and async where the SDK supports it, not just the one the ticket mentioned
- Every callback or setting mode the fix branches on has at least one happy, one sad and one edge cell
- Every pass-through route has a streaming row when the diff touches bytes, SSE or a stream iterator; every hook, callback, metric or logging row has a response-cache-hit twin; every added or changed regex has a pattern-derived worst-case timing row, all on both legs
- Chaos runs include an outage during a concurrent burst and a recovery check that every burst id lands exactly once
- Deterministic: the checked-in head selection passes twice with identical collected and passed selections, no skips, no retries, no `sleep`; live cells run once per leg and a failed live cell is a FAIL row to root cause, never rerun until green
- Both legs run two workers from recorded commit hashes; the report names every hash and never mixes runs
- The PR proof section carries only the latest audit run
- PASS means every inventory row is VERIFIED: executed live on the rig at the head, outcome matched, no mock inside the proxy. Any row listed as not run, skipped, deferred, or proven only through a mocked or patched component makes the verdict FAIL or BLOCKED BY HUMAN
- The final message leads with PASS, FAIL or BLOCKED BY HUMAN

## Advice and Pointers

- `/key/health` is POST. Check the router before assuming a method for any management endpoint
- Anthropic `/v1/messages` and OpenAI `/v1/responses` streaming both need the full stream consumed before the logging callback fires. Read to the end, then look for the id
- Team and key metadata are cached. Set the TTL in the rig config to something the test can outlive or invalidate through the proxy, and assert the effect through `eventually(...)`; a wall-clock wait is how a cell turns flaky on a slow runner
- Two workers means per process state (queues, locks) is tested for real. Route a burst so both workers take traffic and check both worker logs
- The upstream and the sink are `ThreadingHTTPServer`s, never the single-threaded `HTTPServer`: one slow leg would otherwise queue the next and corrupt every timing assertion after the first timeout
- A guardrail or callback that makes its own LLM call from inside a hook (LLM as a judge, prompt rewriting, summarizers) is a recursion risk in `logging_only` mode: the hook sees its own call and judges it again, one chain per request. With the scripted upstream the chain never runs out of credit, so cap it in the test: assert the upstream's received request count for the cell, confirm the internal call is stamped (`metadata->>'internal_call_origin'` on its spend row) and that the hook skips stamped calls only for `logging_only`, then include a cell where a client forges the same stamp and check the enforcing hooks still fire
- A slow or rate limited dependency does not need a mock: add a second router deployment for it with `timeout: 0.001` and another with `rpm: 1`, point one guardrail at each, and drive a small concurrent burst. Expect a mixed result (real verdicts where the call got through, fail open where the router raised) and assert the exact split, not a clean pass
- Name every artifact, report and manifest by the tip SHA it was produced at (`audit_report_<sha>.md`, `phase12/<sha>/`). A rebase mid audit moves both the tip and the merge base, so re-derive `git merge-base origin/main <tip>`, rerun every leg, and grep the final report for the old SHAs before posting; a hit outside the run history section means stale proof
- Post the proof rewrite before the maintainer can merge. `git_update_pr` refuses a merged PR; if the PR merged while the audit was still running, `gh api -X PATCH repos/<owner>/<repo>/pulls/<n>` with a `body` field still replaces the description when the PR was opened by the same bot account
- Chaos spend log loss on the head leg means nothing until the merge base leg loses rows at the same points. Reproduce there first, then root cause it in the queue code (dequeue before write with an exception the retry path does not recognize is the usual shape) and file it as a separate ticket instead of touching it in the audited PR
- Integration contract ids belong to the CircleCI suite; never add them to the separate E2E coverage registry

## Forbidden Actions

- Do not claim a cell passed that you did not run, and do not report a cell that is not a checked-in test
- Do not report PASS while any inventory row is unverified: a not-run, skipped, deferred or mock-proven path anywhere in the report forces FAIL or BLOCKED BY HUMAN
- Do not defer a row to `tests/e2e/` or any other suite, and do not list a row as out of scope; a row that needs the real third party is run live here
- Do not fall back to a live credential inside a deterministic cell when a scripted response is missing; script the response, or make the row an explicit live cell
- Do not mock, patch or stub any litellm component inside the proxy; doubles only at the upstream and destination edges
- Do not run a single worker for the posted proof when the fix touches per process state
- Do not retry, rerun-until-green, `sleep`, or skip; a flaky cell is a FAIL
- Do not mix evidence from different commit hashes in one report
- Do not leave stale proof from earlier runs in the PR body
- Do not stop the shared box Postgres or any process another rig owns
- Do not skip the chaos step because the happy path passed
