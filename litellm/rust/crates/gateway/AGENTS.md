- Keep this crate a thin composition layer: mount endpoint routers and serve the supplied listener
- Server lifecycle and shared inbound middleware belong here, including client authentication, rate limiting, and request logging
- Endpoint paths, request handling, model resolution, and response encoding belong to the mounted crates. Provider execution belongs to the `inference-<fmt>` crates and `llms`
- Inject shared state and infrastructure. Avoid global runtimes, duplicate client pools, and abstractions for hypothetical endpoint groups
- Test mounting and server lifecycle through public HTTP behavior. Test endpoint semantics in the owning crate

## Host
- `src/host/` is the native host, the counterpart of python-bridge's `PythonRouterHost`. `NativeBootHost` answers router-core's deployment build at boot, and `NativeHost` builds a `NativeRouterHost` for each inference call. `Gateway` is gateway-inference's `Gateway<NativeHost>`, so the routes are served through it without depending on it
- A hostcall answered from the gateway's own state belongs here, not in gateway-inference. Only running the route's attempt and authorizing a name stay with the routes

## Admission in front of Python
- In forward mode the supervisor's `LITELLM_FORWARD_CONFIG` names the config file Python loads. With it set, `main.rs` puts the gateway's inference routes in front of the Python proxy, and with it empty it only forwards. Forward mode never reads `LITELLM_CONFIG`, which is the standalone gateway's own setting. MCP is not mounted in front of Python, since a session's requests would split between the two servers
- The library never names forwarding. `src/admit/` only says what the gateway supports, as values. `unsupported` lists what a configuration has that the gateway does not honor, and `Admission::admit` either lets a request in or hands it back with a `Refused`. `main.rs` is the one place that gives those answers to `gateway-forward`, which owns everything about a second server: relaying, the verdict header and its log line. When Python is gone, that crate and the `behind` call go, and `src/admit/` stays
- Admission is an allowlist at every level. The gateway serves a request only when the configuration, the route and the request are each known to be handled the way Python handles them. Never add a check of the form "this needs Python". Add what Rust is known to handle, and leave the rest unsupported or refused
- axum decides the route level. `gateway-forward` sends a path no native route matches and a wrong method to Python, and nothing else lists the native routes
- `Admission::admit` only authenticates. It lets a request in when it has no body, the `gateway-auth-core` planner picks the key path for it as `user_api_key_auth` would, and `Auth::from_config` authenticates its `ApiKey` as the master key. JWT, OAuth2 and public paths are refused, and so is every path that needs a license, since the gateway can't check one, and so is a caller Rust denies or can't decide on, since Python is always right. Each `Refused` variant is one reason, and its snake_case name is the code the verdict header carries. Authorization (`common_checks`) is not run here
- Authentication runs once per request. In front of Python `admit` runs it and hands the caller to the handlers as an extension, and standalone the `authenticate` layer in `router` does. `admitted_router` mounts no authentication layer and `router` never calls `admit`
- `admit/config.rs` is the configuration allowlist, read once at boot. It destructures `Config`, `GeneralSettings`, `RouterSettings`, `LiteLlmSettings` and `Model` in full, so a new field does not compile until it is placed, and a key the config types don't model (`additional_fields`) is unsupported unless it is listed. `unsupported` names every blocker once, never only the first, and boot logs each one, so the log shows how far a configuration is from being served natively. Any blocker leaves every request to Python. router-core's build refuses what it can't route without Python, and `main.rs` turns that refusal into an `Unsupported::Router`, so it is logged and answered like every other blocker and never gets a boot check of its own. Supporting a setting moves it to the ignored bindings, in the same change that makes Rust honor it
- A database is off the allowlist because the native routes write no spend logs and read no keys or DB-stored settings, not because of the config overlay alone. The environment can't be allowlisted, so `environment` lists the variables known to matter, and a variable Python reads that changes a native route's answer belongs there
- TODO: no request body is on the allowlist yet, so every request with one is refused. It needs `is_request_body_safe` and a per-route list of the body fields Rust handles as Python does

## Redis
- `build_redis` builds the Redis clients once at boot (`src/redis/mod.rs`). Components get a clone as a field, never a per-request extractor or a pool. redis-rs multiplexes one connection per node, so there is no connection pool and pool settings like `max_connections` are accepted and ignored
- Which Redis backs which role mirrors the proxy: coordination is `general_settings.coordination_redis`, else the `cache_params` Redis when `cache: true` and `type: redis`, else `REDIS_*` env. The transaction buffer reuses coordination, else env when `use_redis_transaction_buffer` is on. The response cache gets its own client so large values never queue in front of coordination commands
- `src/redis/layers.rs` is the Rust copy of `_merge_redis_kwargs` in `litellm/_redis.py`, which only this host needs because the Python host merges in Python. It puts the configured kwargs over their `REDIS_*` values and fills the `get_secret` fallbacks from the `SETTINGS` rows in `redis-resolve`, under the same conditions Python reads them, then hands the result to `litellm_redis_resolve::interpret`. Values come from a `SecretSnapshot` filled once at boot, read like `get_secret` (secret manager, then environment, with `true` and `false` read as bools), and the only straight environment read is Azure's `REDIS_USERNAME`
- A surface is a `ConfiguredRedis` constructor: `coordination` for `general_settings.coordination_redis`, which rejects a malformed `port` like the proxy's `CoordinationRedisParams` pydantic model, `cache_params` for `litellm_settings.cache_params`, which drops the cache-only keys and reads the `redis_startup_nodes` alias, and `redis_cache_kwargs` for a `RedisCache.redis_kwargs` dict in the contract tests. A new surface is a new constructor, never a flag
- Nulls depend on the surface. `coordination_redis` drops every null like `model_dump(exclude_none=True)`, `cache_params` keeps a null as an explicit `None` that hides the `REDIS_*` value unless `Cache` or `RedisCache` names that parameter, and `RedisCache.redis_kwargs` keeps every null. A missing `os.environ/` reference is a null, as `load_config` resolves it
- A setting the Rust client cannot honor warns and is dropped, and only a security check it cannot enforce fails boot, per `redis-resolve/AGENTS.md`
- Boot never waits for a configured Redis (clients connect lazily). Only the env-only coordination fallback is pinged, for 2s, and treated as absent when unreachable, as in Python
- `/health/readiness` never touches Redis, matching the proxy
