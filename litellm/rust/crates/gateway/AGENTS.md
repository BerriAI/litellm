- Keep this crate a thin composition layer: mount endpoint routers and serve the supplied listener
- Server lifecycle and shared inbound middleware belong here, including client authentication, rate limiting, and request logging
- Inference routes authenticate with `BearerOrXApiKey`, since the proxy accepts an Anthropic `x-api-key` there
- Endpoint paths, request handling, model resolution, and response encoding belong to the mounted crates. Provider execution belongs to the `inference-<fmt>` crates and `llms`
- Inject shared state and infrastructure. Avoid global runtimes, duplicate client pools, and abstractions for hypothetical endpoint groups
- Test mounting and server lifecycle through public HTTP behavior. Test endpoint semantics in the owning crate
- Standalone and in front of Python serve the same native app, built by `native` in `src/main.rs`, with `admit` (`src/admit/mod.rs`) around all of it, so never give one mode a layer the other lacks. The modes differ only in what a refused request gets: Python's answer in front of Python, and a 501 that says why from `alone` when standalone, where nothing else can serve it
- `admit` is the only thing that decides whether the native app answers a request, so it is the only thing that sends one to Python. It sees each request before any layer, and every method and path it admits must have a native route, because a request it admits that no route takes gets the native 404 and is never forwarded to Python
- What `admit` leaves to Python is decided by the checks under Admit below

## Admit
- A request is admitted only when no check names a reason. In front of Python every other request goes to Python as the client sent it, with why in `x-litellm-gateway`. Standalone answers it 501 with why
- `Admit` (`src/admit/mod.rs`) holds what the native app was built from: the config, the deployments the router built from it, the config's model groups (`groups.rs`) and the `Auth` `AppState::auth` builds, which the inference routes authenticate with too. It is built once at boot, and `main` shares it behind one `Arc`. It is only right about the native app built from the same config, so reloading a config, which is not supported yet, has to build both again and replace them together. No config at all is `None` in `main`, which refuses every request as `configuration`
- Each check is a plain sync function in `src/admit/checks/` that reads `Admit` and one part of a request and returns the `Reason` it goes to Python, or `None`. Nothing is decided at boot. The checks run in three stages, each named for what its checks read and each in order, cheapest first: `HEAD` over the request parts (`config::settings`, `head::route`, `head::headers`), `CALLER` over the authentication result (`caller::caller`), `BODY` over the parsed body (`body::fields`, `model::model`). Only `mod.rs` does IO: it authenticates before `CALLER` and reads the body with `body.rs` before `BODY`, so neither happens for a request an earlier stage sent to Python. A new check goes in the stage whose input it reads
- Last, `Admit::model_access` asks `routing::allows`, the question the native route asks of the same router, whether a caller with a model list may call the model it names. A caller that may not goes to Python as `credential`, so Python writes its own 403 `key_model_access_denied`
- A check reads `Admit`: the config, with its environment under it as `litellm_config_load::load` leaves it, the env-only `Environment` `main` read, the router's deployments and whether `STORE_MODEL_IN_DB` is set, never anything looked up while a request is checked. A variable a config key can also hold is read from the resolved config, and a word in it that is no flag is named through `config.origins.unread`
- A `Reason` is the `Refused` the client is told and what it is over: the setting, named as the config spells it or as the variable that set it, or the trait. Each refusal logs what it was over at debug. The header keeps the short reason, never a setting name
- Check what a setting reaches as narrowly as is correct
  - A setting that reaches every request is named in `config.rs`, as a callback or `custom_auth` is
  - A setting Python reads only on one route is named by that route's check, as `use_chat_completions_url_for_anthropic_messages` is in `head::route`
  - A deployment's own setting, or a provider the native route was not compared on, sends its model group to Python, and every group that can fall back to it. The router picks the deployment after the request is admitted, so one deployment sends its whole group. A group sent over a fallback names the group it falls back to in what it is over. Handing a request to Python only once the router falls back would need a handoff after admit, and was left out as not worth it. `tests/admit/groups_and_fallbacks.yaml` shows each case
  - A request trait one setting decides is checked only under that setting, as a coding agent is only while `drop_params` is unset
  - A router setting router-core serves only through a host step the native host does not answer is named in `checks/router.rs`: by `config.rs` when it reaches every call, and by `model` for the groups it reaches, as `model_group_affinity_config` and a routing group's own strategy do. router-core checks no setting when it builds. It asks the host for a step on the calls the setting reaches, and `NativeRouterHost::select` fails such a call. So `admit` is the only guard: both modes build the router from the config as written and put every request to `admit`, and a setting `admit` does not name fails each request it reaches, never the build
- Each config section and `Environment` in `checks/config.rs`, and `LitellmParams` and `Model` in `checks/model.rs`, are destructured field by field, so a new field does not compile until it is honored (`field: _`) or named. A key the config types do not name is always named. Never add a catch-all `..`
- A setting config.yaml and a variable can both set is one field of its config section, filled by `Config::with_environment` in `litellm-config`, and it is checked once, there. Never check its variable as well. Only a setting no config key sets is a field of `Environment`, and a variable Python reads that nobody added to either is not checked
- A database no longer sends a request to Python. The caller check authenticates through `AppState::auth`, which reads it for a virtual key (see Keys)
- `store_model_in_db` sends everything to Python, since Python then serves models and settings from its database on top of the config. `general_settings.store_model_in_db` is named in `config.rs`, and `STORE_MODEL_IN_DB` in the environment overlay is `Admit::stored_models`. A database row that turns it on cannot be seen without reading the database
- `caller::caller` matches every `AuthenticationMethod` `Auth` verifies, with no catch-all, so a way of verifying `Auth` learns does not compile there until it is named native. A caller it does not verify is over the `Error`'s strum name
- A setting is honored when the native app reads it as Python does, or when it only shapes what `admit` never admits: another route, or a caller that holds neither the master key nor a virtual key
- Checks exist only for what the native app lacks. Porting a feature deletes its check in the same change and turns the scenario cases that named it to `expect: rust`, so the change's diff shows each request it stops sending to Python, and finding a new gap adds one with a case that names it. `callers.yaml` holds a case for each kind of caller. Forward only what is opt-in and can be told from the config or the request before any side effect
- A deployment whose model the bundled cost map holds as another model's alias, as `claude-haiku-latest`, sends its group to Python, since Python sends the model the alias stands for and the native app sends the name as written. `Admit::new` reads the aliases once. An alias only a refreshed cost map holds is not seen
- Not ported yet, and not checked either: what Python writes to its database after a call. A request the native app answers gets no spend log row and adds nothing to its key's spend
- `MESSAGES_PROVIDERS` in `checks/model.rs` is the list of providers the native `/v1/messages` has been compared with Python on. Add a provider only with a live comparison
- With a database the proxy looks up the end user a body names in `metadata.user_id` and applies that end user's block, budget and rate limits to any caller. The native app reads no end user, so `body::fields` sends that body to Python as `end_user` whenever `Admit::database` says the proxy has a database
- A request trait that is admitted only because a setting is refused is tied to that setting. Session headers are admitted because no callback or agent reads them and the native app records no spend, so the change that makes callbacks or spend native has to check the traits it does not handle yet
- The body is parsed once. `admit` checks the parsed object by its keys and hands it to the route as the `JsonObject` extension, so the route does not parse it again. Only an admitted request carries it. Whether each value has the right type is left to the route
- Tests come in two kinds. A scenario in `tests/admit/<name>.yaml` is one config and the requests sent to the gateway built from it as `main` builds it in front of Python, each with who answers it, `expect: rust` or `expect: python`, and `tests/admit.rs` lists each file as a case. A request for Python names `reason:`, the reason the client sees. It may also name `over:`, what its `Reason` is over, and a case that stands for one feature Python serves and the native app does not should name it, so the case goes to Python for that feature and not another. Behavior a client can see goes there, including which reason wins when a request trips several checks. A unit test next to a check is kept only for an edge case a scenario would bury (a header spelled oddly, a flag written as text, a fallback shape) or as one example of its kind, never one case per field
- Not checked yet: config Python holds in its database, CLI flags Python was started with, a Redis only `REDIS_*` configures, and environment variables neither `Environment` nor an env-backed config key names
## Keys
- With a database, `AppState::auth` authenticates the master key and a virtual key, in both modes, through `gateway-auth-core`'s `authenticate_key`. `NativeAuthHost` (`src/host/auth/mod.rs`) answers the core's host steps, and reads the key's row from Postgres on every request through `KeyRows`, which tests implement over rows in memory
- With `litellm_settings.enable_redis_auth_cache` on and a coordination Redis, the host first reads the key Python's `UserApiKeyCache` wrote there (`src/host/auth/cached.rs`), and a miss reads Postgres. It never keeps a copy in memory, because this process hears no evictions. A key the native app answers that was read from Postgres is written back to Redis as `cache_key_object` writes it, the row and `last_refreshed_at`, so a key Python never authenticates is not read from Postgres on every request. The write goes through `AuthCache::set_leased` under a lease taken before the row read, so Redis refuses it when any pod evicted the key in between. A key the host declines is never written, since Python answers it and caches it itself. The flag is read as a lax bool, so a quoted `"true"` that Python's `is True` leaves off still reads Redis, which then holds nothing. The master key's hash is never read from the cache, where Python keeps the admin identity and no key row
- A cached key is Python's `UserAPIKeyAuth` dump. The auth fields beyond the row are named in `CachedKey` or `DESCRIBING`, and the rest must be exactly `KeyView`, so a field Python adds is a miss rather than a key served unchecked
- The native app honors a key's expiry, its block, its `models` list, its `rpm_limit`, `tpm_limit` and `max_parallel_requests`, and the `model_rpm_limit` and `model_tpm_limit` maps in its metadata, and nothing else. Its `tpd_limit` is honored by reading nothing, since Python only counts it for a batch and no native route serves one. The list rides on the caller as `Permissions::Models`, which gateway-auth reads the proxy's way, and the limits as `Authentication::limits`. Any other metadata, or a per-model limit that is not a whole number, is declined at the key read. A key that holds anything else is declined (`Error::HostDeclined`), which gateway-auth answers `NotNative` and `admit` leaves to Python as `credential` over `not_native`
- Where a key is declined follows the core's steps. A column the core asks a host step about is declined by that step: `key_owner` for `user_id`, `cached_team` and `key_team` for `team_id`, `project` for `project_id`, `normalize_model` for `aliases`, `key_budgets` for the budget columns. Every other column that holds something is named in `held` (`src/host/auth/key.rs`) and declined at the key read, with an entry of `models` the native app does not read (a pattern like `anthropic/*`, `all-team-models`, `no-default-models`). `held` takes the row apart column by column, so a column added to the row does not compile until it is honored, left to a step or named
- Serving more keys natively means answering one more host step, or honoring a column and taking it out of `held`, in the same change. Never hand the core a key while a column it holds is neither enforced nor declined. The table in `src/host/auth/mod.rs`'s tests sends each column through the host and the core, so a column that stops being declined fails there
- A decline happens while `admit` authenticates the caller, before the body is read and before any limiter counts, so a request that goes to Python over it has counted nothing here
- The key's limits ride on its `Authentication` as `KeyLimits`, and the proxy's `parallel_request_limiter_v3` from `litellm-callbacks-parallel-request-limiter` enforces them as a callback of the stage (`src/callbacks/parallel_request_limiter.rs`), over the coordination Redis or this process's memory. `KeyLimiter::registered` makes each request's `Admission` from its caller. The master key and a key without limits are never refused, as Python builds no descriptor for them, but every caller's tokens are charged after the call, the master key under Python's `litellm_proxy_master_key` and `default_user_id`
- Python checks the limits that need no body twice, and so does the gateway. `middleware::rate_limit::before_body` is `raise_if_over_limit_before_body`, which Python's authentication runs: a route layer inside `authenticate` that only reads the counters and answers `ProxyRateLimitError` in the route's envelope with the limit's headers. The limiter's pre-call hook then counts the call and refuses the limits that need the body, a model's or the tokens a body asks for, and the route answers that refusal as its handler answers any error. The same layer names the key's `x-litellm-key-rpm-limit` and `x-litellm-key-tpm-limit` on every answer of the handler
- The pre-call hook reads the model and the body from the stage. The model becomes the `model_per_key` descriptor under the group `model_group_alias` gives it, through the limiter's own descriptor builder. A name the cost map serves as an alias, such as `claude-sonnet-latest`, is also looked up as the model it stands for (`src/latest_aliases.rs`), so a limit set on either counts the call, and a served call settles its tokens against both. A key with no per-model limit of its own gets the least `default_api_key_rpm_limit` and `default_api_key_tpm_limit` the deployments of the model's group set, the master key included. A token limit reserves the limiter's own estimate of the body, by the route's Python call type, and a body that sets no output cap gets the proxy's implicit one as a patch of its params, a share of the smallest token limit that `NO_MAX_TOKENS_TPM_RESERVATION_FRACTION` sets. `admit` asks `KeyLimiter::counts_tokens` whether a limit counts the call's tokens, and sends a body only Python's estimator reads (one with media) to Python as `body` when one does. Standalone answers that call 501, as it does every request `admit` refuses
- The proxy also checks a model's limits before the router falls back to its group, which the native router does not ask the limiter yet. `checks/model.rs` sends a group that can fall back to one with a default key limit to Python. A key's own per-model limit on a fallback group is not checked yet
- A complete answer gives its parallel slot back in `post_call_success` and carries the `x-ratelimit-*` headers. The success log settles what was reserved to what the route says the call used, as Python's litellm `Usage` (cache tokens folded into the prompt, reads charged less). Messages, chat completions and Responses tell it, a Responses answer converted the way the proxy's success log converts it before its limiter reads it, and transcription tells none yet. A failed call is told without usage, so a stream that breaks is charged nothing where the proxy charges what it had used. `general_settings.token_rate_limit_type` picks which of them a token limit counts. A failed call gives everything back in `post_call_failure`, and a stream the client drops when its `Admission` is dropped
- `admit` hands the caller it authenticated to the route as `Preauthenticated`, which the route's `authenticate` layer takes instead of reading the key again, so an admitted virtual key costs one read. Both are built by `AppState::auth` from the same config, so neither judges the caller differently

## Resources
- `Resources::build` (`src/resources.rs`) makes what every part is built from, once per config: the environment (the config's `environment_variables` in front of the process environment), the `SecretResolver` over it, the HTTP client config and the inference `CoreResources` with the client pool. Inference, Redis and the database each take what they need from it. Never reach into one part for another part's pool, config or secrets, and never build a second environment overlay
- A setting that can come from the environment, the secret manager or OIDC is read through `resources.secrets`. `resources.environment` is only for what Python reads straight from `os.environ`

## State
- `AppState::build` (`src/state.rs`) builds `Resources` and hands them to `AppState::over`, which builds what both modes share once at boot: inference, the Redis clients, the database pools and the key lookup over them. `router` takes it and hands it to routes with `with_state`, and a handler or middleware takes the part it needs with `State<RedisClients>` or `State<Option<Pools>>`, which `FromRef` clones out of it. Never build a store inside a route and never give one mode a store the other lacks
- In front of Python the config is the local YAML file Python loads, which the supervisor names in `LITELLM_FORWARD_CONFIG`. When Python loads no local file, `load_config` cannot load the one it names, or the native app cannot be built from it, `native_state` in `src/main.rs` builds the state from `Config::default()`, so only the environment's `REDIS_*` and `DATABASE_*` are seen, and with no `Admit` every request goes to Python. Never fail boot on that file or on what it sets, because the gateway exiting stops Python too. Config stored in the database is not read yet

## Host
- `src/host/` is the native host, the counterpart of python-bridge's `PythonRouterHost`. `NativeBootHost` answers router-core's deployment build at boot, and `NativeHost` builds a `NativeRouterHost` for each inference call and answers the call's callback hooks from the `Callbacks` it holds. `Gateway` is gateway-inference's `Gateway<NativeHost>`, so the routes are served through it without depending on it
- A hostcall answered from the gateway's own state belongs here, not in gateway-inference. Only running the route's attempt and authorizing a name stay with the routes

## Callbacks
- `src/callbacks/` is the one place a callback runs from, the native counterpart of the proxy's `custom_logger_v2` dispatcher. `Callbacks` holds the callbacks in the order Python runs them, the config's `callbacks` as written and then the proxy's own hooks. `NativeHost` holds it, and a route reaches it only through `litellm_gateway_inference::CallHooks`. Never call a callback's engine from a middleware or a route, and never add a second dispatcher
- A `Call` is one request's hooks. Each hook runs its subscribers in order and hands each the fields its manifest reads. A patch changes what the callbacks after it read, on that hook and on every later one. That is how what one callback publishes reaches another, never a request extension. The first abort on a hook ends it
- `fields.rs` is the only place a contract field is worked out or written, the counterpart of `v2_proxy_fields.py`. A field the gateway cannot work out yet is left out of what a callback is handed, and a write it has no place for is logged and dropped. Add a field there with the first callback that reads it
- A callback that fails or aborts fails the call only on `pre_call` and `post_call_success`, as the proxy raises what those hooks raise. On the other hooks it is logged and the next callback still runs
- A native callback is a file beside `fields.rs` that builds it from the config and adapts its engine to `litellm_callbacks::Callback`, reading typed fields and never Python's kwargs. What Python runs outside its callback list stays outside the stage: the limit check its authentication runs before the body, and the router's own pre-call checks, which belong to router-core
- A callback's tests of whole requests live in `tests/<callback>.rs` and are served through `litellm_gateway::router`. They read a counter through `KeyLimiter::counted`, which exists only under the `test-support` feature the crate's own tests turn on. A test of one function of the callback, like its `Settings::read`, stays inline in its file
- `build_inference` (`src/lib.rs`) builds the callbacks with the router they read, before the gateway that holds them. Only the proxy's own key limiter is registered. No callback is built from a config yet, so `checks/config.rs` still sends every config that names one to Python. The change that builds one deletes its check, and has to check the request traits that callback reads and the stage does not hand it yet
- A callback that keeps something of each request's caller is registered with `Registered::for_caller`, which makes its state for a request from that caller, as Python hands every hook the caller's `UserAPIKeyAuth`. What a callback holds for a call it gives back when that state is dropped, since a stream the client leaves tells no hook

## Redis
- `redis::connect` builds the Redis clients once at boot (`src/redis.rs`). `State<RedisClients>` hands out clones of them, never a connection checked out per request. redis-rs multiplexes one connection per node, so there is no connection pool and pool settings like `max_connections` are accepted and ignored
- Which Redis backs which role mirrors the proxy: coordination is `general_settings.coordination_redis`, else the `cache_params` Redis when `cache: true` and `type: redis`, else `REDIS_*` env. The transaction buffer reuses coordination, else env when `use_redis_transaction_buffer` is on. The response cache gets its own client so large values never queue in front of coordination commands
- Merging a configured block with `REDIS_*` and the `get_secret` fallbacks is `resolve` in `redis-resolve`, which only this host calls because the Python host merges in Python. `src/redis.rs` only picks the `Surface` (`Coordination`, `CacheParams` or `Environment`) and calls it with `resources.secrets`
- A setting the Rust client cannot honor warns and is dropped, and only a security check it cannot enforce fails boot, per `redis-resolve/AGENTS.md`
- Boot never waits for a configured Redis (clients connect lazily). Only the env-only coordination fallback is pinged, for 2s, and treated as absent when unreachable, as in Python
- `/health/readiness` never touches Redis, matching the proxy

## Database
- `db::connect` (`src/db.rs`) builds `litellm_db::Pools`, and the `litellm_repositories::Database` the repositories run their queries on, from `resolve` in `db-resolve`, which takes `general_settings` and `resources.secrets` the way `redis-resolve`'s `resolve` does. No database configured, or a token auth toggle Rust cannot mint for yet, is `None`
- The pools are lazy, so boot never waits for Postgres. A handler takes `State<Option<Pools>>` and picks `writer()`, `read()` or `read_after_write()` per query. Don't add an extractor that checks out a connection, because it would hide that choice
- `/health/readiness` pings the writer for up to 2s and reports `connected`, `disconnected`, or `Not connected` when no database is configured, and always answers 200. The proxy's 503 on `disconnected` without `allow_requests_on_db_unavailable` and its 15s cache of a good answer are not ported

## License
- `AppState::build` verifies the license once at boot with `build_license` (`src/license.rs`) and keeps the result as `entitlements`, which never changes while serving. `middleware::global` hands it to every middleware and route as `Extension<Arc<Entitlements>>`
- The key comes from `LITELLM_LICENSE`, read through `resources.environment` so config `environment_variables` replaces the process environment, and from `general_settings.litellm_license`, which wins unless only the environment's key is enterprise, as in `_use_config_license`. The license server is asked through the `resources` pool and HTTP config
- Verification itself belongs to `litellm-license`. A key the bundled public key did not sign is asked of the license server, so boot can wait on that request for `NON_LLM_CONNECTION_TIMEOUT` seconds per attempt
- The native host holds no `max_parallel_requests` slots yet. `admit` refuses a group whose deployment asks for them, and every request under `default_max_parallel_requests`, so no call the native router runs needs one
