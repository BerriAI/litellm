- Keep this crate a thin composition layer: mount endpoint routers and serve the supplied listener
- Server lifecycle and shared inbound middleware belong here, including client authentication, rate limiting, and request logging
- Inference routes authenticate with `BearerOrXApiKey`, since the proxy accepts an Anthropic `x-api-key` there
- Endpoint paths, request handling, model resolution, and response encoding belong to the mounted crates. Provider execution belongs to the `inference-<fmt>` crates and `llms`
- Inject shared state and infrastructure. Avoid global runtimes, duplicate client pools, and abstractions for hypothetical endpoint groups
- Test mounting and server lifecycle through public HTTP behavior. Test endpoint semantics in the owning crate
- Standalone and in front of Python serve the same native app, built by `native` in `src/main.rs`, with `admit` (`src/admit/mod.rs`) around all of it, so never give one mode a layer the other lacks. The modes differ only in what a refused request gets: Python's answer in front of Python, and a 501 that says why from `alone` when standalone, where nothing else can serve it
- `admit` is the only thing that decides whether the native app answers a request, so it is the only thing that sends one to Python. It sees each request before any layer, and every method and path it admits must have a native route, because a request it admits that no route takes gets the native 404 and is never forwarded to Python
- What `admit` leaves to Python is decided by the checks under Admit below

## Admit
- A request is admitted only when no check names a reason. In front of Python every other request goes to Python as the client sent it, with why in `x-litellm-gateway`. Standalone answers it 501 with why
- `Admit` (`src/admit/mod.rs`) holds what the native app was built from: the config, the router built from it with its deployments, and the `Auth` `AppState::auth` builds, which the inference routes authenticate with too. It is built once at boot, and `main` shares it behind one `Arc`. It is only right about the native app built from the same config, so reloading a config, which is not supported yet, has to build both again and replace them together. No config at all is `None` in `main`, which refuses every request as `configuration`
- Each check is a plain sync function in `src/admit/checks/` that reads `Admit` and one part of a request and returns the `Reason` it goes to Python, or `None`. Nothing is decided at boot. The checks run in three stages, each named for what its checks read and each in order, cheapest first: `HEAD` over the request parts (`config::settings`, `head::route`, `head::headers`), `CALLER` over the authentication result (`caller::caller`), `BODY` over the parsed body (`body::fields`, `model::model`). Only `mod.rs` does IO: it authenticates before `CALLER` and reads the body with `body.rs` before `BODY`, so neither happens for a request an earlier stage sent to Python. A new check goes in the stage whose input it reads
- A check reads `Admit`: the config, with its environment under it as `litellm_config_load::load` leaves it, the env-only `Environment` `main` read, the router and the database fact, never anything looked up outside them while a request is checked. A variable a config key can also hold is read from the resolved config, and a word in it that is no flag is named through `config.origins.unread`
- A `Reason` is the `Refused` the client is told and what it is over: the setting, named as the config spells it or as the variable that set it, or the trait. Each refusal logs what it was over at debug. The header keeps the short reason, never a setting name
- Check what a setting reaches as narrowly as is correct
  - A setting that reaches every request is named in `config.rs`, as a callback or `custom_auth` is
  - A setting Python reads only on one route is named by that route's check, as `use_chat_completions_url_for_anthropic_messages` is in `head::route`
  - A deployment's own setting, or a provider the native route was not compared on, sends its model group to Python, and every group that can fall back to it. The router picks the deployment after the request is admitted, so one deployment sends its whole group. A group sent over a fallback names the group it falls back to in what it is over. Handing a request to Python only once the router falls back would need a handoff after admit, and was left out as not worth it. `tests/admit/groups_and_fallbacks.yaml` shows each case
  - A request trait one setting decides is checked only under that setting, as a coding agent is only while `drop_params` is unset
  - `admit` keeps no reader of the router's settings. `model` asks the router where a request for the name can be served (`Router::reach` in router-core): its model group, every group its fallbacks reach, and the host steps a call served by each one makes beyond its attempt. A name that reaches no model group is `unknown_model`, a fallback target that names none sends the group to Python, and so does a step `answers` in `src/host/router.rs` says the native host does not answer, as another routing strategy, `enable_health_check_routing` and a fallback written as a dict are. Answering a step natively turns its arm of `answers` in the same change. `tests/admit/router_host_steps.yaml` and `fallback_shapes.yaml` show the cases
  - router-core only reports. It checks no setting when it builds and refuses nothing. It asks the host for a step on the calls the setting reaches, and `NativeRouterHost::select` fails such a call. So `admit` is the only guard: both modes build the router from the config as written and put every request to `admit`, and a step `answers` wrongly calls answered fails each request that reaches it, never the build
  - A router setting router-core does not read at all is named by `config.rs` when it reaches every request, and by `checks/router.rs` for the groups it reaches, as `model_group_affinity_config` is
- Each config section and `Environment` in `checks/config.rs`, and `LitellmParams` and `Model` in `checks/model.rs`, are destructured field by field, so a new field does not compile until it is honored (`field: _`) or named. A key the config types do not name is always named. Never add a catch-all `..`
- A setting config.yaml and a variable can both set is one field of its config section, filled by `Config::with_environment` in `litellm-config`, and it is checked once, there. Never check its variable as well. Only a setting no config key sets is a field of `Environment`, and a variable Python reads that nobody added to either is not checked
- A database sends everything to Python, since Python writes a spend log and key spend there after every call, the master key's included. It is `general_settings.database_url`, or `DATABASE_URL`, `DATABASE_HOST`, `IAM_TOKEN_DB_AUTH` or `AZURE_POSTGRESQL_AUTH` in the environment overlay `AppState` holds, which `Admit::new` reads once as `Admit::database`. Writing spend natively, or accepting that a native answer writes none, deletes it
- `store_model_in_db` sends everything to Python, since Python then serves models and settings from its database on top of the config. `general_settings.store_model_in_db` is named in `config.rs`, and `STORE_MODEL_IN_DB` in the environment overlay is `Admit::stored_models`. It stays when the database rule goes. A database row that turns it on cannot be seen without reading the database
- `caller::caller` matches every `AuthenticationMethod` `Auth` verifies, with no catch-all, so a way of verifying `Auth` learns does not compile there until it is named native. A caller it does not verify is over the `Error`'s strum name
- A setting is honored when the native app reads it as Python does, or when it only shapes what `admit` never admits: another route, or a caller the master key does not authenticate
- Checks exist only for what the native app lacks. Porting a feature deletes its check in the same change and turns the scenario cases that named it to `expect: rust`, so the change's diff shows each request it stops sending to Python, and finding a new gap adds one with a case that names it. `callers.yaml` holds a case for each kind of caller Forward only what is opt-in and can be told from the config or the request before any side effect
- A deployment whose model the bundled cost map holds as another model's alias, as `claude-haiku-latest`, sends its group to Python, since Python sends the model the alias stands for and the native app sends the name as written. `Admit::new` reads the aliases once. An alias only a refreshed cost map holds is not seen
- `MESSAGES_PROVIDERS` in `checks/model.rs` is the list of providers the native `/v1/messages` has been compared with Python on. Add a provider only with a live comparison
- A request trait that is admitted only because a setting is refused is tied to that setting. Session headers are admitted because no callback, agent or database reads them, so the change that makes callbacks native has to check the traits it does not handle yet
- The body is parsed once. `admit` checks the parsed object by its keys and hands it to the route as the `JsonObject` extension, so the route does not parse it again. Only an admitted request carries it. Whether each value has the right type is left to the route
- Tests come in two kinds. A scenario in `tests/admit/<name>.yaml` is one config and the requests sent to the gateway built from it as `main` builds it in front of Python, each with who answers it, `expect: rust` or `expect: python`, and `tests/admit.rs` lists each file as a case. A request for Python names `reason:`, the reason the client sees. It may also name `over:`, what its `Reason` is over, and a case that stands for one feature Python serves and the native app does not should name it, so the case goes to Python for that feature and not another. Behavior a client can see goes there, including which reason wins when a request trips several checks. A unit test next to a check is kept only for an edge case a scenario would bury (a header spelled oddly, a flag written as text, a fallback shape) or as one example of its kind, never one case per field
- Not checked yet: config Python holds in its database, CLI flags Python was started with, a Redis only `REDIS_*` configures, and environment variables neither `Environment` nor an env-backed config key names

## Resources
- `Resources::build` (`src/resources.rs`) makes what every part is built from, once per config: the environment (the config's `environment_variables` in front of the process environment), the `SecretResolver` over it, the HTTP client config and the inference `CoreResources` with the client pool. Inference, Redis and the database each take what they need from it. Never reach into one part for another part's pool, config or secrets, and never build a second environment overlay
- A setting that can come from the environment, the secret manager or OIDC is read through `resources.secrets`. `resources.environment` is only for what Python reads straight from `os.environ`

## State
- `AppState::build` (`src/state.rs`) builds `Resources` and hands them to `AppState::over`, which builds what both modes share once at boot: inference, the Redis clients and the database pools. `router` takes it and hands it to routes with `with_state`, and a handler or middleware takes the part it needs with `State<RedisClients>` or `State<Option<Pools>>`, which `FromRef` clones out of it. Never build a store inside a route and never give one mode a store the other lacks
- In front of Python the config is the local YAML file Python loads, which the supervisor names in `LITELLM_FORWARD_CONFIG`. When Python loads no local file, `load_config` cannot load the one it names, or the native app cannot be built from it, `native_state` in `src/main.rs` builds the state from `Config::default()`, so only the environment's `REDIS_*` and `DATABASE_*` are seen, and with no `Admit` every request goes to Python. Never fail boot on that file or on what it sets, because the gateway exiting stops Python too. Config stored in the database is not read yet

## Host
- `src/host/` is the native host, the counterpart of python-bridge's `PythonRouterHost`. `NativeBootHost` answers router-core's deployment build at boot, and `NativeHost` builds a `NativeRouterHost` for each inference call. `Gateway` is gateway-inference's `Gateway<NativeHost>`, so the routes are served through it without depending on it
- A hostcall answered from the gateway's own state belongs here, not in gateway-inference. Only running the route's attempt and authorizing a name stay with the routes

## Redis
- `redis::connect` builds the Redis clients once at boot (`src/redis.rs`). `State<RedisClients>` hands out clones of them, never a connection checked out per request. redis-rs multiplexes one connection per node, so there is no connection pool and pool settings like `max_connections` are accepted and ignored
- Which Redis backs which role mirrors the proxy: coordination is `general_settings.coordination_redis`, else the `cache_params` Redis when `cache: true` and `type: redis`, else `REDIS_*` env. The transaction buffer reuses coordination, else env when `use_redis_transaction_buffer` is on. The response cache gets its own client so large values never queue in front of coordination commands
- Merging a configured block with `REDIS_*` and the `get_secret` fallbacks is `resolve` in `redis-resolve`, which only this host calls because the Python host merges in Python. `src/redis.rs` only picks the `Surface` (`Coordination`, `CacheParams` or `Environment`) and calls it with `resources.secrets`
- A setting the Rust client cannot honor warns and is dropped, and only a security check it cannot enforce fails boot, per `redis-resolve/AGENTS.md`
- Boot never waits for a configured Redis (clients connect lazily). Only the env-only coordination fallback is pinged, for 2s, and treated as absent when unreachable, as in Python
- `/health/readiness` never touches Redis, matching the proxy

## Database
- `db::connect` (`src/db.rs`) builds `litellm_db::Pools` from `resolve` in `db-resolve`, which takes `general_settings` and `resources.secrets` the way `redis-resolve`'s `resolve` does. No database configured, or a token auth toggle Rust cannot mint for yet, is `None`
- The pools are lazy, so boot never waits for Postgres. A handler takes `State<Option<Pools>>` and picks `writer()`, `read()` or `read_after_write()` per query. Don't add an extractor that checks out a connection, because it would hide that choice
- `/health/readiness` pings the writer for up to 2s and reports `connected`, `disconnected`, or `Not connected` when no database is configured, and always answers 200. The proxy's 503 on `disconnected` without `allow_requests_on_db_unavailable` and its 15s cache of a good answer are not ported

## License
- `AppState::build` verifies the license once at boot with `build_license` (`src/license.rs`) and keeps the result as `entitlements`, which never changes while serving. `middleware::global` hands it to every middleware and route as `Extension<Arc<Entitlements>>`
- The key comes from `LITELLM_LICENSE`, read through `resources.environment` so config `environment_variables` replaces the process environment, and from `general_settings.litellm_license`, which wins unless only the environment's key is enterprise, as in `_use_config_license`. The license server is asked through the `resources` pool and HTTP config
- Verification itself belongs to `litellm-license`. A key the bundled public key did not sign is asked of the license server, so boot can wait on that request for `NON_LLM_CONNECTION_TIMEOUT` seconds per attempt
- The native host holds no `max_parallel_requests` slots yet. `admit` refuses a group whose deployment asks for them, and every request under `default_max_parallel_requests`, so no call the native router runs needs one
