- Keep this crate a thin composition layer: mount endpoint routers and serve the supplied listener
- Server lifecycle and shared inbound middleware belong here, including client authentication, rate limiting, and request logging
- Inference routes authenticate with `BearerOrXApiKey`, since the proxy accepts an Anthropic `x-api-key` there
- Endpoint paths, request handling, model resolution, and response encoding belong to the mounted crates. Provider execution belongs to the `inference-<fmt>` crates and `llms`
- Inject shared state and infrastructure. Avoid global runtimes, duplicate client pools, and abstractions for hypothetical endpoint groups
- Test mounting and server lifecycle through public HTTP behavior. Test endpoint semantics in the owning crate
- Standalone and in front of Python serve the same native app, built by `native` in `src/main.rs`, with `admit` (`src/admit/mod.rs`) around all of it, so never give one mode a layer the other lacks. The modes differ only in what a refused request gets: Python's answer in front of Python, and a 501 that says why from `alone` when standalone, where nothing else can serve it
- `admit` is the only thing that decides whether the native app answers a request, so it is the only thing that sends one to Python. It sees each request before any layer, and every method and path it admits must have a native route, because a request it admits that no route takes gets the native 404 and is never forwarded to Python
- What `admit` leaves to Python is decided by the checks under Admit below

## Admit
- A request is admitted only when no check names a reason. In front of Python every other request goes to Python as the client sent it, with why in `x-litellm-gateway`
- A reason says which kind of refusal it is, `Refusal::Unsupported` or `Refusal::Denied`, and the check that names it decides
  - Unsupported: the native app would answer differently from Python, so it never answers. Standalone answers 501 with why
  - Denied: the native app refuses the request too, only in its own words, as a credential the auth core refused. Standalone hands it to the native app, which refuses it
  - A check may name a denial only when a native layer refuses the same request by the same rule before anything is counted or written, since standalone serves whatever the native app does not refuse. A model the caller's lists do not reach stays unsupported for that reason: the native route refuses it only after its pre-call hooks have counted the request. `standalone_leaves_a_denied_request_to_the_native_app_to_refuse` in `main.rs` holds it
  - A request `admit` authenticated carries the result as `Preauthenticated`, the caller or the refusal, and the native app's `authenticate` layer answers from it. So a key is read once per request, and one `admit` refused stays refused even if the key store changed since. `standalone_keeps_a_key_refusal_the_native_app_would_no_longer_make` holds it
  - Only `main.rs` reads the kind. In front of Python both kinds go to Python, so its error body and its failure log stay the proxy's, and `gateway-forward` never sees the difference
- `Admit` (`src/admit/mod.rs`) holds what the native app was built from: the config, the router built from it with its deployments, and the `Auth` `AppState::auth` builds, which the inference routes authenticate with too. It is only right about the native app built from the same config, so the two are held together as one `Served` (`src/live.rs`) and replaced together (see State). No config at all is an `admit` of `None`, which refuses every request as `configuration`
- Each check is a plain sync function in `src/admit/checks/` that reads `Admit` and one part of a request and returns the `Reason` it goes to Python, or `None`. Nothing is decided at boot. The checks run in three stages, each named for what its checks read and each in order, cheapest first: `HEAD` over the request parts (`config::settings`, `head::route`, `head::forwarded_for`, `head::headers`), `CALLER` over the authentication result (`caller::caller`), `BODY` over the parsed body (`body::fields`, `model::model`). Only `mod.rs` does IO: it authenticates before `CALLER` and reads the body with `body.rs` before `BODY`, so neither happens for a request an earlier stage sent to Python. A new check goes in the stage whose input it reads
- Last, `Admit::model_access` asks `routing::allows`, the question the native route asks of the same router, whether a caller's model lists reach the model it names. The answer is `gateway-auth-core`'s `authz::authorize`, never a comparison in `admit`. A caller that may not goes to Python as `credential`, so Python writes its own 403 `key_model_access_denied`
- A check reads `Admit`: the config, with its environment under it as `litellm_config_load::load` leaves it, the env-only `Environment` `main` read, the router and the `StoredConfig` boot read, never anything looked up outside them while a request is checked. A variable a config key can also hold is read from the resolved config, and a word in it that is no flag is named through `config.origins.unread`
- A `Reason` is the `Refused` the client is told and what it is over: the setting, named as the config spells it or as the variable that set it, or the trait. Each refusal logs what it was over at debug. The header keeps the short reason, never a setting name
- Check what a setting reaches as narrowly as is correct
  - A setting that reaches every request is named in `config.rs`, as a callback or `custom_auth` is
  - A setting Python reads only on one route is named by that route's check, as `use_chat_completions_url_for_anthropic_messages` is in `head::route`
  - A deployment's own setting, or a provider the native route was not compared on, sends its model group to Python, and every group that can fall back to it. The router picks the deployment after the request is admitted, so one deployment sends its whole group. A group sent over a fallback names the group it falls back to in what it is over. Handing a request to Python only once the router falls back would need a handoff after admit, and was left out as not worth it. `tests/admit/groups_and_fallbacks.yaml` shows each case
  - A request trait one setting decides is checked only under that setting, as a coding agent is only while `drop_params` is unset
  - `admit` keeps no reader of the router's settings. `model` asks the router where a request for the name can be served (`Router::reach` in router-core): its model group, every group its fallbacks reach, and the host steps a call served by each one makes beyond its attempt. A name that reaches no model group is `unknown_model`, a fallback target that names none sends the group to Python, and so does a step `NativeHost::unanswered` in `src/host/router.rs` says the native host does not answer for that group, as another routing strategy, `enable_health_check_routing` and a fallback written as a dict are. `admit` holds the host and asks it, so it reads none of the host's state itself. Answering a step natively turns its arm of `unanswered` in the same change. `tests/admit/router_host_steps.yaml` and `fallback_shapes.yaml` show the cases
  - router-core only reports. It checks no setting when it builds and refuses nothing. It asks the host for a step on the calls the setting reaches, and `NativeRouterHost::select` fails such a call. So `admit` is the only guard: both modes build the router from the config as written and put every request to `admit`, and a step `unanswered` wrongly calls answered fails each request that reaches it, never the build
  - A router setting router-core does not read at all is named by `config.rs` when it reaches every request, and by `checks/router.rs` for the groups it reaches, as `model_group_affinity_config` is
  - `router_settings.enable_pre_call_checks` is honored, since the native host answers the pre-call facts (see Host). `unanswered` answers that step per group: a group still goes to Python as `model` when `ContextWindows` holds no context window for one of its deployments, since the proxy's own cost map may hold one the bundled one does not. `admit` asks the host, which answers from the same `ContextWindows` its calls read, and never reads the setting itself. How a prompt is counted sends nothing to Python: the native app holds a prompt to its own estimate (see Host), so a tool call, media and an OpenAI-named model stay native. `tests/admit/pre_call_checks.yaml` shows each case
- Each config section and `Environment` in `checks/config.rs`, and `LitellmParams` and `Model` in `checks/model.rs`, are destructured field by field, so a new field does not compile until it is honored (`field: _`) or named. A key the config types do not name is always named. Never add a catch-all `..`
- A setting config.yaml and a variable can both set is one field of its config section, filled by `Config::with_environment` in `litellm-config`, and it is checked once, there. Never check its variable as well. Only a setting no config key sets is a field of `Environment`, and a variable Python reads that nobody added to either is not checked
- `general_settings.allowed_ips`, `use_x_forwarded_for` and `allowed_routes` are read by `gateway-auth-core`'s `Allowlists`, the rules the Python proxy reads them with. `middleware::request_allowlist` refuses a request they leave out with the proxy's 403, on the routes Python authenticates and before the credential is read, as `pre_db_read_auth_checks` does. `admit` asks the same question after `HEAD` and admits such a request as sent, without reading its caller or body, so the native app answers that 403 in both modes
  - The address is the TCP peer, or the `x-forwarded-for` header as sent when `use_x_forwarded_for` is on, as Python reads it. With it off Python checks the address its own server resolved, which reads that header from a peer the operator trusts, and the gateway is not told who that is. So `head::forwarded_for` leaves a request that sends the header to Python while `allowed_ips` is set
  - The route is the path a native route matched, with `root_path` taken off. Python decodes percent escapes before it matches and axum does not, so a path that spells a native route with an escape is no native route to `head::route` either, and goes to Python in front of it and to a 501 standalone
- A database no longer sends a request to Python. The caller check authenticates through `AppState::auth`, which reads it for a virtual key (see Keys)
- With `store_model_in_db` on, boot layers the config the proxy stores in its database into the config (see State), so every check sees stored settings and models as if the file held them, and a stored callback, guardrail setting or secret manager goes to Python like one in the file. `StoredConfig::Unread`, a database boot could not read, sends every request to Python as `db_config_not_loaded`. With the stored config loaded, each kind of stored object the proxy loads beside it that a native route reaches and the gateway does not read, read as `StoredObjects` with the stored rows (a default-on guardrail, a policy attachment, a tool policy other than `untrusted`, cache settings, a secret manager override, a beta headers or cost map reload; `holds` in `stored.rs` maps each to its kind), sends every request to Python while the database holds one, unless `general_settings.supported_db_objects` leaves the kind out. The poller swaps when one comes or goes
- `caller::caller` matches every `Credential` of the `Caller` the auth core hands back, with no catch-all, so a caller the native host learns to serve does not compile there until it is named native. A credential the core did not authenticate is over the `Error`'s strum name
- A setting is honored when the native app reads it as Python does, or when it only shapes what `admit` never admits: another route, or a caller that holds neither the master key nor a virtual key
- Checks exist only for what the native app lacks. Porting a feature deletes its check in the same change and turns the scenario cases that named it to `expect: rust`, so the change's diff shows each request it stops sending to Python, and finding a new gap adds one with a case that names it. `callers.yaml` holds a case for each kind of caller. Forward only what is opt-in and can be told from the config or the request before any side effect
- A deployment whose model the bundled cost map holds as another model's alias, as `claude-haiku-latest`, sends its group to Python, since Python sends the model the alias stands for and the native app sends the name as written. `Admit::new` reads the aliases once. An alias only a refreshed cost map holds is not seen
- With a database, the native app writes a served call's spend log row and charges its key's spend counters through the proxy's spend log callback (see Callbacks). A call is charged only once it carries a `Cost`, which the native app does not price yet, so until then the callback raises its failed tracking alert and writes nothing. A failed call writes no failure row yet. What Python does after a row is written (session spend totals, tool usage, request error counts, the cached key's spend, alerts) is not ported and not checked
- `MESSAGES_PROVIDERS` in `checks/model.rs` is the list of providers the native `/v1/messages` has been compared with Python on. Add a provider only with a live comparison
- A request trait that is admitted only because a setting is refused is tied to that setting. Session headers are admitted because the native app reads them the way Python does: the call record's layer (`gateway-inference/src/record/trace.rs`) gives the call the `litellm_trace_id` that `get_chain_id_from_headers`, then a `traceparent`, then a fresh id give it in Python, and the spend log row names it as its session. The session's spend totals are not kept natively
- The body is parsed once. `admit` checks the parsed object by its keys and hands it to the route as the `JsonObject` extension, so the route does not parse it again. Only an admitted request carries it. Whether each value has the right type is left to the route
- Tests come in two kinds. A scenario in `tests/admit/<name>.yaml` is one config and the requests sent to the gateway built from it as `main` builds it in front of Python, each with who answers it, `expect: rust` or `expect: python`, and `tests/admit.rs` lists each file as a case. A request for Python names `reason:`, the reason the client sees. It may also name `over:`, what its `Reason` is over, and a case that stands for one feature Python serves and the native app does not should name it, so the case goes to Python for that feature and not another. Behavior a client can see goes there, including which reason wins when a request trips several checks. A unit test next to a check is kept only for an edge case a scenario would bury (a header spelled oddly, a flag written as text, a fallback shape) or as one example of its kind, never one case per field
- Not checked yet: CLI flags Python was started with, a Redis only `REDIS_*` configures, and environment variables neither `Environment` nor an env-backed config key names
## Keys
- With a database, `AppState::auth` authenticates the master key and a virtual key, in both modes, through `gateway-auth-core`'s `authenticate_key`. `NativeAuthHost` (`src/host/auth/mod.rs`) answers the core's host steps. It reads a key through `AuthStore` in `src/host/auth/store.rs`, the gateway's `UserApiKeyCache`: this process's memory, with the coordination Redis behind it when `litellm_settings.enable_redis_auth_cache` is on, in front of `auth-store`'s `KeyDatabase::read`, the read the Python proxy makes too. As in Python the flag only decides whether Redis is attached, so without it a key is still kept in memory for 60 seconds, never read from the database on every request
- `cached_key` reads the cache alone, and `db_key`, which the core calls only after that missed, reads the database and caches what it found, so with Redis attached a miss costs one Redis read and one write. The store caches every key it finds, in the bytes Python caches it in, whoever ends up answering the request. It takes no lease, as Python's `cache_key_object` takes none, so a key evicted while its row was being read can be cached again until it expires. The flag is read as a lax bool, so a quoted `"true"` that Python's `is True` leaves off still reads Redis, which then holds nothing. The master key's hash is never read from the cache, where Python keeps the admin identity and no key row
- The store keeps a copy of each key in this process's memory, so `state.rs` subscribes to the invalidation channel the Python pods publish evictions on (`hear_evictions`) whenever a coordination Redis exists, with the flag on or off, as Python's `start_cache_invalidation_subscriber` does. A gateway that read through the store without it would keep answering for a blocked key until its copy expired. With no coordination Redis nothing carries an eviction, so a key blocked on a Python pod answers from the gateway's copy until it expires, as it does from every other Python worker's
- A cached key is Python's `UserAPIKeyAuth` dump, typed as `CachedKey` in `redis-store`. A field this build does not name is kept beside the named ones, and a key that holds something in one is declined, since a newer pod wrote a limit this build cannot honor. An entry that does not decode is a miss, and the database answers
- Tests that need a key store it in a real Postgres through `tests/keys/mod.rs` (`Held`), which unit tests include by path. There is no in-memory key source
- The native app honors a key's expiry, its block, its `models` list, its `rpm_limit`, `tpm_limit` and `max_parallel_requests`, and the `model_rpm_limit` and `model_tpm_limit` maps and the `priority` text in its metadata, and nothing else. Its `tpd_limit` is honored by reading nothing, since Python only counts it for a batch and no native route serves one. The model list, the limits and the priority are fields of the key's row, read once in `host/auth/key.rs`. `host::layers` hands the list to the auth core as the caller's key layer, and the core's `authz::authorize` reads it the proxy's way. An entry that rule does not read, a provider pattern such as `anthropic/*`, `all-team-models` or `no-default-models`, declines the key at the read, and so does any other metadata or a per-model limit that is not a whole number. A key that holds anything else is declined (`Error::HostDeclined`), which gateway-auth answers `NotNative` and `admit` leaves to Python as `credential` over `not_native`
- Where a key is declined follows the core's steps. A column the core asks a host step about is declined by that step: `key_owner` for `user_id`, `cached_team` and `key_team` for `team_id`, `project` for `project_id`, `normalize_model` for `aliases`, `key_budgets` for the budget columns. Every other field that holds something is named in `held` (`src/host/auth/key.rs`) and declined at the key read, with an entry of `models` the native app does not read (a pattern like `anthropic/*`, `all-team-models`, `no-default-models`). `held` takes the cached key apart field by field, so a field added to `CachedKey` does not compile until it is honored, left to a step or named
- Serving more keys natively means answering one more host step, or honoring a column and taking it out of `held`, in the same change. Never hand the core a key while a column it holds is neither enforced nor declined. The table in `src/host/auth/mod.rs`'s tests sends each column through the host and the core, so a column that stops being declined fails there
- A decline happens while `admit` authenticates the caller, before the body is read and before any limiter counts, so a request that goes to Python over it has counted nothing here
- The key's limits are `KeyLimits`, a type that lives beside the limiter and that the key's row holds as a field. The limiter's `Caller::of` reads them off the core's `Caller`, with the key named by `Caller::hash` and the master key by Python's `litellm_proxy_master_key`. The proxy's `parallel_request_limiter_v3` from `litellm-callbacks-parallel-request-limiter` enforces them as a callback of the stage (`src/callbacks/parallel_request_limiter.rs`), over the coordination Redis or this process's memory. `KeyLimiter::registered` makes each request's `Admission` from its caller. The master key and a key without limits are never refused, as Python builds no descriptor for them, but every caller's tokens are charged after the call, the master key under Python's `litellm_proxy_master_key` and `default_user_id`
- Python checks the limits that need no body twice, and so does the gateway. `middleware::rate_limit::before_body` is `raise_if_over_limit_before_body`, which Python's authentication runs: a route layer inside `authenticate` that only reads the counters and answers `ProxyRateLimitError` in the route's envelope with the limit's headers. The limiter's pre-call hook then counts the call and refuses the limits that need the body, a model's or the tokens a body asks for, and the route answers that refusal as its handler answers any error. The same layer names the key's `x-litellm-key-rpm-limit` and `x-litellm-key-tpm-limit` on every answer of the handler
- The pre-call hook reads the model and the body from the stage. The model becomes the `model_per_key` descriptor under the group `model_group_alias` gives it, through the limiter's own descriptor builder. A token limit reserves the limiter's own estimate of the body, by the route's Python call type, and a body that sets no output cap gets the proxy's implicit one as a patch of its params. `admit` sends a body only Python's estimator reads (one with media) to Python as `body` when the key counts tokens. Standalone answers that call 501, as it does every request `admit` refuses
- A complete answer gives its parallel slot back in `post_call_success` and carries the `x-ratelimit-*` headers. The success log settles what was reserved to what the route says the call used, as Python's litellm `Usage` (cache tokens folded into the prompt, reads charged less), which only `/v1/messages` tells yet. `general_settings.token_rate_limit_type` picks which of them a token limit counts. A failed call gives everything back in `post_call_failure`, and a stream the client drops when its `Admission` is dropped
- `admit` hands the caller it authenticated to the route as `Preauthenticated`, which the route's `authenticate` layer takes instead of reading the key again, so an admitted virtual key costs one read. Both are built by `AppState::auth` from the same config, so neither judges the caller differently

## Resources
- `Resources::build` (`src/resources.rs`) makes what every part is built from, once per config: the environment (the config's `environment_variables` in front of the process environment), the `SecretResolver` over it, the HTTP client config and the inference `CoreResources` with the client pool. Inference, Redis and the database each take what they need from it. Never reach into one part for another part's pool, config or secrets, and never build a second environment overlay
- A setting that can come from the environment, the secret manager or OIDC is read through `resources.secrets`. `resources.environment` is only for what Python reads straight from `os.environ`

## State
- `AppState::build` (`src/state.rs`) builds `Resources` and hands them to `AppState::over`, which builds what both modes share once at boot: inference, the Redis clients, the database pools and the key lookup over them. `AppState::next` builds the state of a new config over the current one, keeping what lives as long as the process: the Redis clients, the database pools and key store with its eviction subscriber, the license, the HTTP client pool and provider auth (`Resources::sharing`), the deployments' `RoutingCache` and the limiters' counters. Only the environment overlay, the router and the callbacks over it are built again. A setting that picks one of the kept parts (a Redis, the database URL, the license, `enable_redis_auth_cache`) takes effect at the next restart `router` takes it and hands it to routes with `with_state`, and a handler or middleware takes the part it needs with `State<RedisClients>` or `State<Option<Pools>>`, which `FromRef` clones out of it. Never build a store inside a route and never give one mode a store the other lacks
- In front of Python the config is the local YAML file Python loads, which the supervisor names in `LITELLM_FORWARD_CONFIG`. When Python loads no local file, `load_config` cannot load the one it names, or the native app cannot be built from it, `native_state` in `src/main.rs` builds the state from `Config::default()`, so only the environment's `REDIS_*` and `DATABASE_*` are seen, and with no `Admit` every request goes to Python. Never fail boot on that file or on what it sets, because the gateway exiting stops Python too
- `load_config` (`src/stored.rs`) is the one boot path both modes take. It reads the file, and when `store_model_in_db` is on (the file, `STORE_MODEL_IN_DB`, or the stored `general_settings` row) it reads the `LiteLLM_Config` settings rows, the stored models and the credentials once, decrypts every stored string with `LITELLM_SALT_KEY` or else the master key, and layers them into the file's document before any `os.environ/` reference is read, as `litellm_config_load::Document` lays out. A stored model that does not load is skipped with a warning. A database that cannot be read never fails boot. The file alone is served and `admit` refuses every request as `db_config_not_loaded` until a later read loads. A shadowed stored key and a credential no source holds are logged as warnings. When `store_model_in_db` is on, the pool boot read through is kept in the `Source` it returns, for the poller
- Both modes serve from `Live` (`src/live.rs`), which holds the current `Served`: the `AppState`, the `Admit` over it and the native app built from both, made by `served` in `src/main.rs`. `Live::swap` replaces the whole `Served` at once, one swap at a time, and its build gets the current one, so it can reuse what should outlive a config. A request `Live::admitted` admits carries the `Served` that admitted it, and `Live::native` answers it from that one, so a swap between admit and the native app never splits a request across two configs and a request in flight finishes where it started. Never hold a part of `Served` outside it, or a swap leaves it behind. The `InFlight` counter is the process's, shared by every `Served`
- The poller (`src/reload.rs`) is the only thing that swaps. `polled` in `src/main.rs` starts it in both modes when boot read the stored config from a database, and stops it before the pools close. Every `general_settings.proxy_config_reload_interval_seconds`, else `PROXY_CONFIG_RELOAD_INTERVAL_SECONDS` (30 when neither is a positive integer), it reads the stored rows as boot does, and when the decrypted rows equal the ones served it builds nothing. Otherwise it layers them over the file document boot read, which is never read again, logs what changed by model id, credential name and settings key, never a value, and swaps to a `Served` built with `AppState::next` and an `Admit` over `StoredConfig::Loaded`, so the first read that loads lifts `db_config_not_loaded`. A stored setting a kept part is built from (a Redis, the database) that differs from boot is warned about by name on every read, since it takes a restart
- With a coordination Redis, the same Redis and namespace Python's `redis_usage_cache` resolves to, `src/config_sync.rs` also listens on `litellm_proxy.config_change`, where Python's writers announce each config write, and reads again 1s plus up to 5s of jitter after a change, at most once per 10s, as `ConfigSyncSubscriber` paces it. A subscription that was lost reads once when it is back. Every read, polled or announced, goes through the one `Reloader` and its locked `Reading`, so two never run at once or disagree on what is served. The poll keeps running as the fallback, and a spawned task awaits a reload only boxed (`boxed_reload`), since its future is too deep to lay out inline in a release build
- Python's guards against a database blip hold in the poller. A model or credential read that fails changes nothing, a settings read that fails keeps the settings last served and removes no model, and a config that does not build keeps the current one. Never let a failed read reach the router as an empty model list

## Host
- `src/host/` is the native host, the counterpart of python-bridge's `PythonRouterHost`. `NativeBootHost` answers router-core's deployment build at boot, and `NativeHost` builds a `NativeRouterHost` for each inference call and answers the call's callback hooks from the `Callbacks` it holds. `Gateway` is gateway-inference's `Gateway<NativeHost>`, so the routes are served through it without depending on it
- A hostcall answered from the gateway's own state belongs here, not in gateway-inference. Only running the route's attempt stays with the routes
- `src/host/precall.rs` answers `RouterHost::pre_call_facts`, and router-core decides with them. A route hands its prompt over through `RouteAttempt::prompt`, typed by its format, and only `/v1/messages` does. Every route implements it, and one that answers `None` has its calls held to no window, as a chat or Responses call would be, and `admit` admits neither in either mode. A call's prompt is counted once, on `NativeRouterHost`, however many retries and fallbacks ask for the facts. The count is an estimate standing in for the provider's tokenizer, so each deployment's facts mark it `estimated` and router-core keeps a deployment it overflows by up to twice its window, as it does Python's stand-in count, except a deployment whose own `model_info.max_input_tokens` caps the cost map's window, which holds exactly. Each deployment's context window is `get_router_model_info`'s merge, run by router-core over `NativeModelInfoHost` (`src/host/model_info.rs`), which answers its cost-map reads from the bundled cost map, so the deployment's own `model_info.max_input_tokens` wins. A window depends on the deployment and the cost map alone, so `build_inference` reads every one once into `ContextWindows`, which `NativeHost` holds. A call and `admit` read that one table, so they hold to the same window. Never read a window per request, and rebuild `ContextWindows` with `Admit` when the cost map changes. No region is reported, since only an end user sets one and the gateway reads none yet, so router-core's region stage is not wired here and `admit` leaves a key that carries a region to Python. No requested param is reported either, since `admit` leaves a body that names `response_format` to Python. The cost map is the bundled one until the gateway refreshes its own
- `src/host/prompt_estimate.rs` is the only place that decides how a prompt is counted for those checks, and its module doc is the contract. It is an estimate on purpose: text, the `system` block and the tools are counted as the proxy counts them, and everything else by a rule written there (a block the counter does not read as the text of its JSON, media at a flat count, always `cl100k_base`). Never send a request to Python over how its prompt is counted, and never count a prompt anywhere else. A new way a prompt differs from the proxy's count is a line in that doc and a test beside it, and a new route's format is a new variant of `routing::Prompt` and a new arm of `Countable::of`

## Auth
- `src/host/auth` is the native `AuthHost`, the counterpart of python-bridge's `PythonAuthHost`. `auth` there builds the one `Auth` the inference routes and `admit` authenticate with, so the master key is verified by `gateway-auth-core` whether or not a database is configured, and a virtual key by the same call when one is. Never verify a credential anywhere else
- The gateway owns its rows, `NativeRows`. Each field of a cached row is read once, in `host/auth`, into the facts the core decides on, and a field this host does not serve declines the key there. Nothing after authentication reads a row's column again
- A type one consumer reads lives beside that consumer, as a limiter's view of a key lives with the limiter. `host/auth` holds only what the core's steps ask of it
- An `Infallible` row in `NativeRows` means an association this host does not serve. No identity that needs one exists, and a step that would need one declines, before any counter is written. A key has a row, `host::auth::Key`, and its owner, team, project and the rest are `Infallible`, so a key that names one is declined
- A key whose row has no stored hash is declined at the read, and the core refuses one too, so every key that is a caller is named by `Caller::hash`. Never name a key by the token a request presented

## Callbacks
- `src/callbacks/` is the one place a callback runs from, the native counterpart of the proxy's `custom_logger_v2` dispatcher. `Callbacks` holds the callbacks in the order Python runs them, the config's `callbacks` as written and then the proxy's own hooks. `NativeHost` holds it, and a route reaches it only through `litellm_gateway_inference::CallHooks`. Never call a callback's engine from a middleware or a route, and never add a second dispatcher
- A `Call` is one request's hooks. Each hook runs its subscribers in order and hands each the fields its manifest reads from the call's record, which it reaches through `record::read` and `record::write`, never a field of its own. A turn that finds no record fails, so a hook that decides ends the call rather than admitting it unchecked. A patch changes what the callbacks after it read, on that hook and on every later one. That is how what one callback publishes reaches another, never a request extension. The first abort on a hook ends it
- `src/callbacks/fields.rs` is the only place a contract field is worked out from the call's record or written to it, the counterpart of `v2_proxy_fields.py`. The record itself (`litellm_gateway_inference::record`) holds typed entries and knows nothing of contract fields. A field the gateway cannot work out yet is left out of what a callback is handed, and a write it has no place for is logged and dropped. Add a field there with the first callback that reads it
- `Point` in `mod.rs` lists every hook the stage runs and how it ends, so a new hook is a new variant there and never a branch in `run`. A callback that fails or aborts ends the call only on `pre_call` and `post_call_success`, as the proxy raises what those hooks raise. On the other hooks it is logged and the next callback still runs, and a manifest that may abort on one of them is refused at registration, since the stage has nowhere to send that refusal
- What a callback returns is held to its subscription by `Subscription::check`: a patch outside its declared writes or an abort without `may_abort` is that callback's failure, never applied
- A failure reaches the route as `HookError::Failed` with its cause kept, and only `gateway-inference/src/error.rs` turns it into text. An abort is `HookError::Refused`, in the callback's own status and words
- The request body is the only place the model and the stream flag are read from while the pre-call hook holds it (`Request` in `record/entries.rs`), so a patch to it is what the next callback reads. Never cache a value next to the body it came from
- A native callback is a file in `src/callbacks/` that builds it from the config and adapts its engine to `litellm_callbacks::Callback`, reading typed fields and never Python's kwargs. What Python runs outside its callback list stays outside the stage: the limit check its authentication runs before the body, and the router's own pre-call checks, which belong to router-core
- A callback's tests of whole requests live in `tests/<callback>.rs` and are served through `litellm_gateway::router`. They read a counter through `KeyLimiter::counted`, which exists only under the `test-support` feature the crate's own tests turn on. A test of one function of the callback, like its `Settings::read`, stays inline in its file
- `build_inference` (`src/lib.rs`) builds the callbacks with the router they read, before the gateway that holds them, and registers them in the order the proxy does: the config's `callbacks`, then the proxy's own key limiter, then with a database its spend log callback. `dynamic_rate_limiter_v3` is the only config callback built, so `checks/config.rs` still sends a config that names any other to Python. The change that builds one deletes its check, and has to check the request traits that callback reads and the stage does not hand it yet
- `src/callbacks/spend_log.rs` is the proxy's spend log callback over the engine in `litellm-callbacks-spend-logger`, registered last when a database is configured. `RustSpendLogHost` (`src/host/spend_log.rs`) answers its host calls, through `Registered::hosted`, whose turn runs the callback's hosted handler and answers each host call it yields (`src/callbacks/hosted.rs`). The writer flushes from the gateway's own loop every `PROXY_BATCH_WRITE_AT` seconds and drains at shutdown, since Python's spend log monitor runs only in Python. `SpendLog` lives in `AppState` for the life of the process, so a reloaded config registers the same callback and writer
- `src/callbacks/model_capacity.rs` is `dynamic_rate_limiter_v3` over the engine in `litellm-callbacks-model-capacity`, on the key limiter's counters, with `NativeCapacityHost` (`src/host/capacity.rs`) answering the engine's host calls from the active teams registry. Its pre-call hook publishes its statuses as a patch, which the key limiter after it reads as the answer it starts its own from. A config whose `priority_reservation_settings` lists a `borrow_idle_capacity` entity goes to Python, since a limit that borrows needs a token estimate and reservation the native host does not answer
- A callback that keeps something of each request's caller is registered with `Registered::for_caller`, which makes its state for a request from that caller, as Python hands every hook the caller's `UserAPIKeyAuth`. What a callback holds for a call it gives back when that state is dropped, since a stream the client leaves tells no hook

## Redis
- `redis::connect` builds the Redis clients once at boot (`src/redis.rs`). `State<RedisClients>` hands out clones of them, never a connection checked out per request. redis-rs multiplexes one connection per node, so there is no connection pool and pool settings like `max_connections` are accepted and ignored
- Which Redis backs which role mirrors the proxy: coordination is `general_settings.coordination_redis`, else the `cache_params` Redis when `cache: true` and `type: redis`, else `REDIS_*` env. The transaction buffer reuses coordination, else env when `use_redis_transaction_buffer` is on. The response cache gets its own client so large values never queue in front of coordination commands
- Merging a configured block with `REDIS_*` and the `get_secret` fallbacks is `resolve` in `redis-resolve`, which only this host calls because the Python host merges in Python. `src/redis.rs` only picks the `Surface` (`Coordination`, `CacheParams` or `Environment`) and calls it with `resources.secrets`
- A setting the Rust client cannot honor warns and is dropped, and only a security check it cannot enforce fails boot, per `redis-resolve/AGENTS.md`
- Boot never waits for a configured Redis (clients connect lazily). Only the env-only coordination fallback is pinged, for 2s, and treated as absent when unreachable, as in Python
- `/health/readiness` never touches Redis, matching the proxy

## Database
- `db::connect` (`src/db.rs`) builds `litellm_db::Pools`, and the `litellm_repositories::Database` the repositories run their queries on, from `resolve` in `db-resolve`, which takes `general_settings` and `resources.secrets` the way `redis-resolve`'s `resolve` does. No database configured, or a token auth toggle Rust cannot mint for yet, is `None`
- The pools are lazy, so boot never waits for Postgres. A handler takes `State<Option<Pools>>` and picks `writer()`, `read()` or `read_after_write()` per query. Don't add an extractor that checks out a connection, because it would hide that choice
- `/health/readiness` pings the writer for up to 2s and reports `connected`, `disconnected`, or `Not connected` when no database is configured, and always answers 200. The proxy's 503 on `disconnected` without `allow_requests_on_db_unavailable` and its 15s cache of a good answer are not ported
- A gateway `fips` cargo feature, when it is added, must enable `litellm-at-rest/fips`, so a FIPS build cannot read or write a stored value with the NaCl cipher. With `general_settings.fips_mode` on, `stored.rs` derives the at-rest key with `KeyDerivation::FipsKbkdf` from `LITELLM_SALT_KEY` alone, and when that fails it leaves every request to Python, never falling back to the SHA-256 key

## License
- `AppState::build` verifies the license once at boot with `build_license` (`src/license.rs`) and keeps the result as `entitlements`, which never changes while serving. `middleware::global` hands it to every middleware and route as `Extension<Arc<Entitlements>>`
- The key comes from `LITELLM_LICENSE`, read through `resources.environment` so config `environment_variables` replaces the process environment, and from `general_settings.litellm_license`, which wins unless only the environment's key is enterprise, as in `_use_config_license`. The license server is asked through the `resources` pool and HTTP config
- Verification itself belongs to `litellm-license`. A key the bundled public key did not sign is asked of the license server, so boot can wait on that request for `NON_LLM_CONNECTION_TIMEOUT` seconds per attempt
- The native host holds no `max_parallel_requests` slots yet. `admit` refuses a group whose deployment asks for them, and every request under `default_max_parallel_requests`, so no call the native router runs needs one
