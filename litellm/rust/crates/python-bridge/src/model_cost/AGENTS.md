# Model cost bridge

- `NativeModelCostMap` holds inputs only, the installed `CostMap`, kept `Registrations` and the name index. Python's `litellm.model_cost` is the only copy of the live rows
- Every call that reads or writes rows takes the dict as an argument. Never store rows or build a second table here
- `LiveDict` holds a reference to that same dict and reads it under the GIL on every query, so a Python write is seen on the next read
  - It needs the GIL, so Rust code running without the GIL cannot use it
  - Its stamp is the dict's address, length and last key. [model-catalog/src/store/AGENTS.md](../../../model-catalog/src/store/AGENTS.md) says what that misses
- `host.rs` is the only code that calls Python, by name through `MODULE`. Calls happen with the GIL held and no `NativeModelCostMap` lock held
  - `resolve` reaches `find_key` on this same object, so holding a lock across a host call deadlocks
  - Test `a_host_lookup_that_reaches_find_key_on_the_same_map_finishes` guards this
- Rows and registrations cross as Python objects, never JSON, because router `model_info` holds `datetime`
- `table::build` serves the document as main's `_expand_model_aliases` did, so all names of a model share one row object made by `host.entry`
- `install` touches no state until `CostMap::read` succeeds. `NativeRejected` means nothing changed
- `register` keeps a registration only after its pass finished, so an exception in a host call keeps nothing
- `rows=None` writes each entry into whichever table is published at that moment and never reports a swap
- `cost_snapshot` is the pricing view of the published table, a `CostSnapshot` in `snapshot.rs` over the same name index. `host::generation` reads the table, its generation and the Python-held state pricing reads (the discount and margin configs and the `fallback_generalizations` rules) in one call, and the snapshot is rebuilt only when the generation or the configs' values move. Model-catalog's `CostLookup` only reads it through `CatalogView`, so every Python-shaped concern (generation, swap, row cache) lives here
  - `CostSnapshot::lookup` hands one pricing call a `CallView`, which reads each row from Python once, so the call sees one version of every row it reads
  - Lowerings are kept by row key and billed provider together with the fields they were lowered from, and reused only while the row reads exactly those fields. A row replaced or edited in place is lowered again on the next call, with no `changed_in_place()` needed
  - `invalidate` drops the current snapshot along with the name index, so the next call reads the rules and names again
  - Tests that install a fake host module hold `HOST_MODULE`, since Python can switch threads while one runs
- `refresh_blocking` and `fetch_blocking` run on a throwaway runtime with an unpooled client so an importing process can still fork. `refresh` is for workers after the fork
- `refresh_blocking` and `refresh` fetch and read off the GIL and touch no state. `install_refreshed` is the only step that needs the GIL, since it builds the table
- A blocking refresh runs on a daemon thread, and a thread that comes back from native code once the interpreter is finalizing aborts the process on Linux. `CostMapRefreshStop.stop` ends the fetch and returns only after `refresh_blocking` has left native code, so Python calls it from `atexit`. Each refresh takes a stop of its own, so a forked child never waits on a lock its parent's thread held
