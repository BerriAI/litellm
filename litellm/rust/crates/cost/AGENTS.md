The price vocabulary (meter, band, channel, `When`, `Billing`) is explained in [../model-catalog/AGENTS.md](../model-catalog/AGENTS.md#concepts), the only crate that maps it to JSON keys

## Layout

- `price`, `bound` and `rates` are the three entry points, and `RowSource` (`row.rs`) is the only way they reach a row. Model Catalog implements it over its per-call snapshot, so this crate never reads the cost map, never merges rows and holds no provider list beyond the pricing rules it ports
- `engine.rs` hands each `PriceQuery` kind to its handler module. A kind or case without a handler answers `Unpriced::NotPorted`, and only then may the caller price it the old way
- `tokens.rs` and `tokens/` port `cost_per_token` for every provider and the token path of `completion_cost`: `rule.rs` for which provider branch prices a row and what it adds to `generic_cost_per_token` (the basis facts it reads, uplifts, the web search fee, a cost the provider stated), `branch.rs` for the branches with a formula of their own (a row billed by the second, Vertex AI's legacy 128k bands and character pricing, Perplexity, Dashscope, free branches), `breakdown.rs` for the values main stores beside the total, `custom.rs` for `custom_cost_per_token`
  - `decisions.rs` prices a `/v1/decisions` or `/v1/systemone` call: a provider that bills per request bills its query price (`decisions_request_price`), and a row with `_decisions` prices bills them in place of the online ones of the same meter and condition (`Prices::decisions_view`)
  - `TokenRules` says which path the caller took: a provider branch, `generic_cost_per_token` (with every basis fact or the service tier alone) or `requested_model_info_override`. The caller looks the row up the way its branch did and passes it, so the core never repeats a provider's name rewrite
  - The receipt carries what `completion_cost` stored beside the total: `BreakdownRow` names the row the token-type breakdown and billed rates read (the priced row, the candidate's catalog row, a row the caller looked up apart, or none), `tools` are the built-in tools the call used (priced by `tools.rs`), and `RouterFee` bills the Azure AI Model Router fee on the prompt or as the `Azure Model Router Flat Cost` part. The breakdown and the savings quote the row at the call's tier and endpoint whatever the branch read
- `tools.rs` ports the built-in tool fees (`StandardBuiltInToolCostTracking` and the web search and Maps grounding calculators `llms/__init__.py` dispatches to): each provider's web search calculator, the price per call it falls back to, Maps grounding, the Responses image generation tool, file search, and Azure's vector store, computer use and code interpreter, added in main's order. The caller reads the counts off the response and looks up the rows each calculator read, naming them by index (`Tools<usize>`) until the bridge resolves them to `RowRef`s. `PriceQuery::Tools` prices them alone, one calculator or a whole call, and a token call carries them in `TokensQuery::tools`
- `reported.rs` bills a cost a provider or the gateway in front of it reported, named by its source (`ReportSource`): the `llm_provider-x-litellm-response-cost` header bills as reported and an OpenAI-compatible upstream's `usage.cost` takes the discount and margin, and both split the billed total between prompt and completion in the ratio the catalog prices the call's usage (`split_reported_cost_by_cost_map_ratio`), which the caller passes. A provider billed from its own usage fields (`usage.cost` of xAI and Perplexity) stays with its token branch, and `Receipt::reported` makes the reported figure the cost before discount and margin
- `adjust.rs` ports the discount and margin config. Rules keep the order the config wrote them in
- Each per-unit kind has its own module (`rerank.rs`, `vector_store.rs`, `ocr.rs`, `speech.rs`, `transcription.rs`, `search.rs`, `video.rs`, `image.rs`), which picks the meter and quantity main's calculator billed. `units.rs` holds what they share: the rows a header names, `PriceSource::Rows` (the deployment's own price tables, read ahead of the catalog row in the order the kind's calculator reads them), billing one row through `calculate`, and the receipt with the query's discount and margin settled
  - Where main billed a call nothing on purpose (no row, no rate, no units) the core answers `Unpriced`, never 0.0, and the adapter maps it to each calculator's legacy return
  - `image.rs` also bills the per-image fallback of the Vertex AI, Gemini, Bedrock, gpt-image and Tencent calculators, and a Vertex AI call served at a regional endpoint carries the priced row's uplift (`Adjustments::regional_endpoint`), the one rule the model group display reads through the bridge too
- `batch.rs` prices one line of a batch output file from the row its caller resolved, reading each rate the way main's batch helpers read its key. `price_many` prices many queries against one `RowSource`, so the bridge lowers each row of a batch output file once and crosses into the core once per file
- `session.rs` prices a realtime or Live session in one crossing: its tokens at the first candidate row that bills them something or declares a price, and each `response.done` turn on its own row, both by `generic_cost_per_token`'s rules on the receipt's prompt and completion, and Live voice seconds, xAI audio seconds and text messages, translation seconds and transcription clips as one receipt part each, from the rows the caller lists in the order main tries the session's models. A Responses websocket session split by service tier is still split and summed in Python, one token call per tier
- The fee kinds (`a2a.rs`, `mcp.rs`, `guardrail.rs`) price what the caller configured (`PriceSource::PerQuery`, `FlatPerToken`, an MCP server's tool prices, Azure Prompt Shield's price per thousand records) or the guardrail rows the header lists. A hook-set `response_cost` that beats them stays in the adapter. A call billed as several separately priced units lists each in `Receipt::parts`, where a unit no price covers stays `Unpriced` and never reads as free

## Parity fixtures

`fixtures/*.json` were captured once from main's Python with `LITELLM_LOCAL_MODEL_COST_MAP=True`. Each case holds its inputs (the row fields it read, the billed usage, the config) and main's outputs, and the `parity` test module of each kind asserts Rust equals them to the last bit. Never replay Python from a test. When a fixture must change, recapture it from main and say why in the commit
