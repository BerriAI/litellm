# rules

- Claude on Azure AI Foundry: reuses `anthropic/messages` shaping with the Azure `/anthropic` path
- Auth follows Python's `BaseAzureLLM._base_validate_azure_environment` order: the call's key, `litellm.api_key`, `litellm.azure_key`, `AZURE_OPENAI_API_KEY`, `AZURE_API_KEY`, each skipped only when empty, sent as `x-api-key`
- Without a key, and only when a Python host is wired in (`AzureAdTokenHosts::host`), the config walks Python's `get_azure_ad_token` order, reading every setting from the call and then where Python reads it: `AZURE_AD_TOKEN` through the secret lookup (`get_secret_str`, deferred through `deferred_secret_names`), the other Entra variables from the process environment (`os.getenv`), all only when no key or caller credential is present. A static token, the caller's provider and client secret run natively (`litellm-auth-azure`). Username and password, OIDC references, `os.environ/` references, an uncallable provider and token refresh go to the host's `get_azure_ad_token`, so Python orders and mints those. No token sends the call unauthenticated. Without a Python host, as in the Rust gateway, a missing key is the `MissingApiKey` error main raised, whatever Entra ID settings the deployment holds
- The base is Python's `api_base or get_secret_str("AZURE_API_BASE")`: `AZURE_API_BASE` is a deferred secret read only when the call's base is empty, and the URL is cut at `/anthropic` in the path only, untrimmed, as `azure_anthropic_messages_url` does
- Deliberate differences from Python, approved by the owner: a caller `x-api-key`, `api-key` in any casing or `Authorization` other than a blank bearer is the only credential sent. A caller `api-key` goes out as `x-api-key` in any casing when it replaces a deployment key. Without one it is sent as Python sends it, renamed to `x-api-key` only when spelled exactly `api-key` No deployment key and no Entra ID token goes beside or over it, and the Entra ID path is never run
- `anthropic-beta` goes through the `azure_ai` row of `anthropic_beta_headers_config.json` as Python's handler filters it: unknown and unsupported betas are dropped, the caller's and the ones the request needs alike
- The beta-gated system field strip, system-role normalization and the `cache_control.scope` strip run in `finalize_request`, after the betas are picked from the request as sent, in the order Python's transform runs them
- This config alone reads messages and system prompts Rust could not type as Python does (`UnparsedMessages::Read`): the sanitizer, advisor and encrypted-reasoning strips rewrite them and their beta triggers count. Every other provider, `anthropic` included by the owner's ruling, keeps main's behaviour: such messages go as sent, and a system prompt that does not parse is main's request error (`messages_body`)
