- Expose a mountable Axum router. Listener binding, server lifecycle, and shared inbound middleware belong to `gateway`
- Own endpoint paths, request parsing, model alias resolution, and API-specific response and SSE error formats. Delegate hosted call execution and HTTP body delivery to host-http
- Delegate inference execution to the `inference-<fmt>` crates and provider transformations and authentication to `llms` and the auth crates. Do not duplicate them in handlers
- Let the `inference-<fmt>` crates validate inference fields and supported features, then map their errors to HTTP responses. Do not add gateway checks for temporary inference limitations
- Use injected deployments, HTTP pools, settings, and secret sources. Do not load process configuration or construct independent clients in handlers
- Test HTTP contracts here, including status codes, forwarded headers, error envelopes, and streaming behavior. Keep inference and provider tests in their owning crates
- Routes go through router-core in `routing.rs`: `call` authorizes the name and hands the core a `RouteAttempt` per route. Every other hostcall is answered by the `Host` the `Gateway<H>` was built with. This crate implements no router-core host trait, so the routes never learn which host serves them
- A streamed attempt is served deferred, so the core only counted its request. `stream_outcome.rs` watches the stream's events as they pass and tells the core how it went: a success with the tokens the stream counted once it ends, or a failure when it breaks or carries the provider's error event. A Messages error event is the failure the same error is before a stream opens, with the status of `MessagesErrorType::status`, so a 400-type event cools nothing down and an overloaded one does. This differs from the Python proxy on purpose, which records a stream that goes out with an error event as served. A new streaming route wraps its chunks with `reporting_outcome`
- `stream_event.rs` holds the one reader of each stream format, which says for an event whether content began, what it counts and whether it is the provider's error with the answer that error gets before a stream. `stream_outcome.rs` and `stream_hold.rs` ask that reader and never read a format themselves. A new format adds its reader there, matching on the format's event type in `llms-types` instead of reading raw JSON
- A served stream is held in `routing::call` while it has sent no content and the core says a retry or a fallback could still answer (`stream_hold.rs`). When the provider fails it there, by an error event or a break, the core's `take_over_stream` decides whether an attempt may answer in its place and runs the retry in its group and then the fallbacks. `routing.rs` orders none of that itself and starts from the `origin` on the response it was handed. The failed stream is closed before the take-over runs, a stream no attempt may answer for goes out as the provider sent it, and a take-over that serves nothing ends the call on the provider's error as an HTTP answer, with the routing headers of the stream that failed. The stream that answers is held the same way. A route opts in by answering `RouteAttempt::held` with its stream and the reader of its format. Keepalives are held with the rest, since the response head is only written once the stream settles
- An error the core makes itself is answered in Python's status and words. `routing::call` turns the core's no-deployments refusal into `NoDeployments`, which reads as `RouterRateLimitError` does. Add a variant the same way before a new core refusal can reach a client, never the core's own `Display` text
- `routing::timeout` is the one place an attempt's timeout is decided, in the order of Python's `resolve_llm_passthrough_timeout`. The request's own `timeout` and the service-tier timeouts are not read yet
