# Очередь запросов при достижении лимита параллелизма модели

## Обзор

Добавлена настройка `general_settings.model_concurrency`, которая ограничивает количество одновременно выполняемых запросов для группы моделей. Когда лимит достигнут, новый запрос ожидает освобождения слота вместо немедленного отклонения.

## Конфигурация

```yaml
general_settings:
  model_concurrency:
    gpt-4o:
      limit: 5                    # макс. параллельных запросов для этой группы моделей
      queue_timeout_seconds: 60   # время ожидания слота (по умолчанию 60)
      max_queue_size: 100         # сколько запросов может ждать слот одновременно (по умолчанию 100)
```

## Ключевые решения

- **Ключ лимита** — группа модели (то, что клиент передаёт как `model`), общий для всех пользователей/ключей
- **Хранение слотов** — в Redis-гауге v3-лимитера, поэтому все воркеры/реплики прокси делят один счётчик
- **Таймаут** — если слот не освободился за `queue_timeout_seconds`, возвращается 429 с `RateLimitType.CONCURRENT_REQUESTS`
- **Сессия** — один HTTP-запрос занимает один слот на всё время жизни, включая стриминг
- **Интервал опроса** — 0.1 секунды (`MODEL_CONCURRENCY_QUEUE_POLL_INTERVAL_SECONDS`)

## Где стоит ожидание

Слот модели берётся в pre-call хуке **после** проверок RPM и `max_parallel_requests` ключа/команды. Поэтому собственные лимиты тенанта ограничивают и глубину его очереди, а запрос, который всё равно получил бы 429 по RPM или параллели, не занимает место в очереди и не перехватывает освободившийся слот у легитимного запроса. Проверка выполняется и при пустом наборе дескрипторов, то есть на инсталляции без лимитов ключей лимит модели всё равно работает.

## Ограничение очереди

Ожидание ограничено с двух сторон.

- `queue_timeout_seconds` — сколько ждёт один запрос
- `max_queue_size` — сколько запросов может ждать одновременно (по умолчанию 100)

Если очередь заполнена, новый запрос получает 429 сразу, не вставая в неё. Счётчик ожидающих ведётся на процесс, а не на кластер: защищается локальный ресурс (задача ожидания и её опрос Redis), а глобальный счётчик потребовал бы TTL-уборки на случай падения воркера посреди ожидания.

Дополнительно время ожидания урезается остатком `total_timeout` запроса. `total_timeout_held` снимает дедлайн на всё время pre-call хука, поэтому без этого ограничения запрос с `x-litellm-total-timeout: 10` мог бы просидеть в очереди минуту, занять слот и быть убитым сразу после хука.

## Батч-запросы

Запрос с несколькими моделями через запятую (`model: "gpt-4o,gpt-4o"`), включая `fastest_response`, отклоняется с 429, если хотя бы у одной из перечисленных групп настроен `model_concurrency`. `route_llm_request` разбивает такую строку и вызывает роутер напрямую, поэтому вложенные вызовы не проходят через pre-call хук и один слот не может покрыть их все. Вместо тихого обхода лимита возвращается ошибка с просьбой слать по одному запросу на модель.

Та же особенность касается RPM и `max_parallel_requests` ключа: батч обходит и их. Системное исправление возможно только на уровне роутера или ядра, где происходит диспатч, и остаётся отдельной задачей.

## Метрики Prometheus

Глубина очереди отдаётся как gauge на эндпоинте `/metrics`:

```
litellm_model_concurrency_queue_size{model_group="gpt-4o"}
```

- Метка `model_group` — та же группа модели, для которой задан лимит
- Значение — сколько запросов **в этом воркере** прямо сейчас ждут свободный слот
- Запрос, получивший слот с первой попытки, в метрике не появляется
- Запрос уходит из метрики при получении слота, таймауте и отмене клиентом

Gauge создаётся лениво, при первом запросе, который встал в очередь. Пока очередь ни разу не заполнялась, серии с этой меткой может не быть. Это нормальное поведение Prometheus, `rate`/`sum` по отсутствующей серии даёт пустой результат.

С `PROMETHEUS_MULTIPROC_DIR` метрика использует `multiprocess_mode="livesum"`, поэтому scrape внутри пода суммирует ожидающих по всем воркерам. Между репликами прокси сумма считается на стороне Prometheus. Запрос для панели Grafana:

```promql
sum by (model_group) (litellm_model_concurrency_queue_size)
```

Проверить, что метрика отдаётся:

```bash
curl -s localhost:4000/metrics | grep litellm_model_concurrency_queue_size
```

Таймаут ожидания отдаётся клиенту как 429 с `rate_limit_type="concurrent_requests"`, отдельной метрики для таймаутов очереди нет.

## Пример работы

```
sequential first  (200, 0.68, "hello")      # первый запрос прошёл
sequential second (200, 0.53, "hello")      # второй прошёл после освобождения слота
concurrent fast   (200, 0.53, "hello")      # один из параллельных занял слот
concurrent queued (200, 1.15, "hello")      # второй ждал ~0.6с и прошёл
while streaming   (429, 1.02, "...")        # во время стриминга слот занят → таймаут
stream            (200, 2.04, "6 chunks")   # стриминг завершился
after stream      (200, 0.53, "hello")      # слот освобождён, запрос прошёл
```

## Ограничения

1. **Legacy v1-лимитер** (`LEGACY_MULTI_INSTANCE_RATE_LIMITING=true`) не поддерживает эту функцию
2. **Нет лимита глубины очереди** — каждый ожидающий запрос опрашивает каждые 0.1с до таймаута
3. **Поле не в UI** — `model_concurrency` не добавлено в `ConfigGeneralSettings.model_fields`, поэтому UI управления БД не будет его автодополнять

## Детали реализации

### Acquire (занятие слота)

1. В `async_pre_call_hook` вызывается `_await_model_concurrency_slot`
2. Резолвится группа модели через `_model_group_resolver`
3. В цикле с интервалом 0.1с вызывается `parallel_acquire` в Redis
4. При успехе слот сохраняется в `stash.model_concurrency_slot`
5. При таймауте выбрасывается `ProxyRateLimitError` с 429

### Release (освобождение слота)

Слот освобождается через `_release_stashed_model_concurrency_slot` во всех существующих путях:

- `async_post_call_success_hook` — успешный ответ
- `async_post_call_failure_hook` — ошибка провайдера
- `async_release_max_parallel_requests_on_disconnect` — обрыв соединения
- `async_post_call_streaming_iterator_hook` — конец стриминга

### Отказоустойчивость

- При недоступности Redis деградирует к in-memory счётчику (по умолчанию)
- При `fail_closed_rate_limit_enforcement: true` — возвращает 503 вместо деградации
- TTL слота: 1 час (`PARALLEL_REQUEST_SLOT_TTL_SECONDS = 3600`), утечки самоисправляются
