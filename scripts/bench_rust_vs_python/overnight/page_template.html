Rust /v1/messages baseline on main

Overnight benchmark of the newest main on the Rust Messages path, with S3 and Prometheus logging on. Every number below is the median across 48 runs of the same frozen traffic, with a bootstrap 95% interval. The flame graph merges 7 profiled runs taken at the same load.

Under load, 5 requests a second

Open-loop arrivals, 60 s warmup then 240 s measured per run. Requests use a 45k to 55k token input with tools and stream 1k to 4k output tokens from a mock that paces tokens at 12.5 ms. 1,474 requests per run, all 70,752 succeeded and were counted in both S3 and Prometheus.

One request at a time

One user and an instant mock, 300 warmup then 1,500 measured requests per run. This isolates CPU per request. The next request starts the moment the previous stream ends, so logging work that runs after the stream closes lands on the next request's pre-upstream time. That is why time to first token is higher here than under load.

How stable the numbers are

Each dot is one run, in the order they ran overnight. Blue and orange are two names for the same build, interleaved, so any gap between them is pure machine noise. They agree within 0.4% on every metric. The machine itself got about 2.5% slower in the second half of the night, visible in both kinds of runs, so absolute numbers carry roughly that much host drift.

What stands out

18.1ms / req

Rebuilding the streamed response for logging is a fifth of all CPU

build_complete_streaming_response reassembles every streamed chunk into one response for the logging callbacks. #51487 moved it off the client's critical path, but it still costs 18 ms per request, 12.6 ms of it in stream_chunk_builder. This is the largest single target.

6.3ms / req

Pydantic attribute misses inside that rebuild

pydantic.BaseModel.__getattr__ runs for every in, .get and field probe on the chunk objects that misses a declared field. The hot callers are _assembled_message_fields, extract_usage_chunk and _field_of in streaming_chunk_builder_utils.py, going through __contains__ and __getitem__ in types/utils.py. Reading fields directly or caching which fields exist would remove most of it.

10.3ms / req

Success logging callbacks

async_success_handler and what it calls, including Prometheus at 5.0 ms and S3 at 1.0 ms. Prometheus label sanitising alone is 0.6 ms of self time.

5.4ms / req

Auth before the model call

FastAPI dependency resolution takes 5.4 ms, and 5.0 ms of that is user_api_key_auth, with a virtual-key cache and no database. Router selection on the Python side adds 7.0 ms by subsystem.

1.1ms / req

A database error is raised and handled twice per request with no database configured

The Prometheus user budget metric (_assemble_user_object) and auth (_safe_fetch) both go through the DB metrics wrapper, which catches an exception and runs is_exception_related_to_db. That does a module lookup with filesystem stats every time. A cheap fix is to skip the lookup when no database is set up.

1.1ms / req

The Rust logger takes the GIL to check whether logging is enabled

_native::logger::enabled attaches to the interpreter on each log call from _settle and the stream iterator. Caching the level on the Rust side would remove the GIL round trips.

23.4ms / req

Rust code and the crossing into Python

Rust itself is 20.2 ms, mostly JSON serialisation and payload building. Converting values between Python and Rust (pythonize, json_from_py) is another 3.3 ms.

These rows overlap where one function calls another, so they don't sum to the total.

Method and caveats

Each round ran a load pair (N then Nb, order shuffled) and a sequential pair, with a profiled run after every third round, so all three kinds share the night's drift. Every run starts a fresh proxy, mock, S3 server and Prometheus directory. The proxy is pinned to cores 0 and 1, Locust to core 2 and the mock and S3 to core 3. Locust stayed under 9% of its core. Every streamed response carried the Rust header, and the non-streaming ones are served by Rust as well because the Python handler for this deployment only refuses.

Profiled runs are never measured runs. py-spy slows the proxy, so the flame graph gives shares and the milliseconds come from the unprofiled load runs. The first profiled run lost 23 in-flight streams the moment py-spy attached and is left out of the merge. While building this I found that flame.py cut stacks at 60 frames, which charged about 30% of samples to the wrong frames. It now keeps 512 frames.

CPU per request is higher under load (91 ms) than one at a time (71 ms). At 5 req/s, fixed background work such as timers and metrics collection is spread over fewer requests, and concurrent streams add scheduling overhead.
