# litellm-cost

This crate calculates token and non-token charges from rates and usage supplied by its caller. It is standalone and has no Python bridge or proxy integration

Call `compile(&pricing)` once for an immutable plan, then `plan.calculate(&request)` for each supported request. `calculate(&pricing, &request)` compiles on each call. A successful result exposes pre-multiplier component costs, selected rates, the multiplier, and derived `input()`, `output()`, and `total()` values

`non_token::calculate` totals priced units such as images, pixels, seconds, pages, requests, credits, and guardrail units. `non_token::calculate_image` selects the first available price from ordered pricing tables, with per-image rates ahead of per-pixel rates inside each table. `non_token::calculate_ocr_with_tables` selects each OCR rate from the first table that has it, then `non_token::calculate_ocr` prefers credit pricing when credits are present and otherwise prices pages and annotation pages. `non_token::calculate_ocr_batch` uses deployment batch or standard rates for each page family, then published rates and the page rate as an annotation fallback. `non_token::calculate_video` selects a video-specific per-second rate, then a resolution rate, then the base per-second rate. Unpriced OCR and video usage returns zero, as in Python. Invalid quantities and rates return errors

`ocr_cost` reads OCR response usage, layers deployment and published rates, bills reported credits first, and distinguishes missing page usage from zero pages. `batch::batch_cost_from_model_info` selects each flat or threshold batch rate from model metadata, applies modality prices and regional uplift, and uses the regular-rate fallback where Python does

`openai_cost` exposes Python's transcription cost route and video price selection from caller-supplied model metadata. It selects the video-specific rate, then the resolution rate, then the base output rate. `groq_cost` prices executed browser searches and opens separately; the built-in tool dispatcher uses the same function

`batch::get_batch_cost_rates` selects input, output, cache read, and cache creation rates independently at the highest crossed threshold. `batch::batch_cost_calculator` applies batch modality rates, cache rates, the regular-rate half-price fallback, and an optional regional multiplier to normalized usage. The caller supplies model prices, provider threshold policy, regional multiplier, and token details

`guardrail_cost` selects regional or base Bedrock guardrail rates from a caller-supplied cost map, preserves unknown per-counter prices, prices Azure Prompt Shield text records, validates hook cost stamps, and merges guardrail charges into a cost breakdown

`tool_call_cost_tracking` detects chat annotations and Responses output items, counts billable web-search calls, and prices web search, file search, vector storage, computer use, and code interpreter sessions from model metadata and caller-supplied fallback rates. `tool_cost_dispatch::get_cost_for_built_in_tools` applies Python's search, file-search, and Azure assistant precedence, including Gemini and provider-specific web-search usage. `ModelInfoCatalog::completion_cost` can calculate the built-in tool charge from a response. The caller supplies model metadata, response kind, and any configurable fallback rates

`retrieval_cost` prices rerank search units or tokens according to the selected provider and prices Vertex Search API queries. `ModelInfoCatalog` routes those branches through caller-supplied model metadata

`completion_cost` joins caller-supplied token, built-in tool, and additional costs, then applies provider discount and margin configuration in Python's order. It also parses provider-reported response cost and preserves the cache-hit, provider-cost, calculated-cost precedence. `ModelInfoCatalog` exposes these operations for the generic token and per-second paths

`CompletionCost` keeps input, output, built-in tool, and additional charges alongside discount and margin totals. Response WebSocket tier results sum each component across tiers

`cost_breakdown::cost_breakdown` turns those totals and optional token charges into Python's logging breakdown fields. The caller supplies named additional charges and the pricing basis; no Python logging object is mutated

`response_cost_calculator_from_response` checks a cache hit and provider-reported hidden cost before calling response pricing. Numeric strings and booleans follow Python's float conversion for reported cost

`billed_token_rates` resolves the rates used for cache-read, cache-write, and reasoning spend, including TTL splits, off-peak windows, service tiers, token thresholds, and regional uplifts. The breakdown carries those rates so callers can report cost and rate from the same selection. `provider_cache` applies the Fireworks cache-read default to both generic totals and breakdowns

`prompt_caching_savings` calculates the read discount minus cache-write premium at the request's selected rates, including TTLs, off-peak windows, thresholds, service tiers, and regional uplift

`image_response_cost` prices complete image response token usage before a caller falls back to per-image pricing. It preserves image input rates when input details are present and treats unclassified output tokens as text. The Gemini and Vertex image-generation wrappers add web-search grounding, prefer token usage, and otherwise charge per returned image. Gemini image edits share generation billing; Vertex image edits use the shared flat image rate. Catalog lookup merges supplied deployment metadata over the shared model entry for Gemini

`perplexity_cost` uses a reported total when present, including a cost object normalized from Responses usage. Its manual path prices flat or off-peak tokens, citations, reasoning tokens, and search requests. `ModelInfoCatalog::cost_per_token` dispatches this provider to that calculation

`xai_cost` accepts a finite nonnegative provider total or folds reasoning tokens into older raw completion counts before generic pricing. It also mirrors server-side web-search usage and prices those calls, unless a provider total already covers them. `ModelInfoCatalog::cost_per_token` dispatches xAI through this path

`dashscope_cost` selects one tier from total input tokens, bills cache reads and writes at that tier, and applies flat off-peak overrides. It preserves explicit zero reasoning rates and the model-level output fallback for input-only tiers. `ModelInfoCatalog::cost_per_token` dispatches Dashscope and its two brand aliases through this path

`fireworks_cost` resolves an unmapped model to the same parameter-size category used by Python, then applies the Fireworks cache-read default and generic off-peak rates. Exact model prices take priority. The category thresholds are caller-configurable in the standalone helper, with Python's current defaults used by `ModelInfoCatalog`

`together_cost` checks whether an exact registry row has an input rate, then maps unmapped chat and embedding models to Python's parameter-size categories. `ModelInfoCatalog::cost_per_token` applies chat fallback; `ModelInfoCatalog::together_ai_cost_per_token` accepts the call type for embedding fallback. The helper accepts caller-supplied thresholds, while the catalog uses Python's defaults

`search_cost` prices search-only calls with per-query rates or max-results tiers. Its Parallel AI path selects a mode price, prefers provider-reported request and extra-result SKUs, and otherwise estimates extra results from request parameters. `ModelInfoCatalog::search_provider_cost_per_query` exposes both routes

`speech_cost` selects character or token rates for speech, uses output-only generation pricing for caller-supplied Lyria metadata, and selects token or duration pricing for transcription. The duration helper follows Python's output-rate precedence so duplicate input and output rates are billed once

`speech_cost::count_characters` mirrors Python's whitespace-excluding character count. `completion_cost_from_response` uses a caller-supplied speech prompt when an explicit character count is absent

`azure_ai_cost` detects Model Router names and fee entries. `ModelInfoCatalog::azure_ai_cost_per_token` prices the response model and adds the routing fee once when the priced or requested model used the router. Missing router deployments bill the fee alone; missing non-router models return an error. The generic catalog method dispatches Azure AI through this route when no request model is supplied

`completion_cost_from_response` also reads the original Azure AI router name from response hidden parameters when the selected response model names only the served model. A hidden router name takes precedence over a caller-supplied non-router request name, and the fee is billed once

When the served Azure AI model has its own price, `completion_cost_from_response` keeps the router fee in named additional costs, matching Python's cost breakdown. Direct `cost_per_token` calls continue to include the fee in prompt cost

`azure_ai_image_cost` prefers token usage, then the returned-image rate, then dimension-based pixel pricing. It accepts request dimensions or response size, explicit image count, and deployment price overrides. `ModelInfoCatalog::azure_ai_image_generation_cost` resolves the model metadata and exposes the route without changing Python billing

`image_cost_router` recognizes Python's image response call types, normalizes supplied deployment prices, and routes Vertex, Gemini, Azure AI, Recraft, AI/ML, CometAPI, RunwayML, fal.ai, Bedrock, and OpenAI/Azure GPT image generation through the matching Rust calculators. Recraft, AI/ML, CometAPI, and RunwayML share per-returned-image pricing. The default route selects quality and size keys in Python's order, then applies deployment prices

`bedrock_image_cost` chooses Titan, Nova Canvas, Stability 3, or Stability 1 config behavior by model name. Titan, Nova, and Stability 3 bill returned images from the model entry. Stability 1 selects a size and step-tier catalog key before applying its per-image rate

`fal_ai_image_cost` prices deployment per-image rates first, then keyed quality and size rows, then model-level per-image or rounded megapixel rates. It also selects passthrough rates by resolution. The standalone catalog supplies the same keyed rows that Python reads from its global model map

`openai_image_cost` follows GPT image billing precedence: chat usage with an output breakdown, image token usage, chat usage without a breakdown, then flat per-image pricing. It uses the shared image token helper and generic token calculator so image input and output token rates are applied to their reported modalities

`azure_cost` applies Azure speech's output-per-second rate when response time is present, even if token rates exist. `databricks_cost` maps legacy endpoint prefixes to registry keys before generic token pricing. The Lemonade route returns zero for unmapped and token-priced local models. The Python cost calculator's earlier wall-clock branch still applies when eligible

`anthropic_cost` applies the served fast-speed multiplier after generic token pricing. The generic calculator already applies the provider-specific geo multiplier, so the Anthropic route does not apply geo twice. The module also reads Anthropic web-search counts from usage or raw responses and prices the direct usage path

`realtime_cost` collects and combines response usage from realtime and Responses WebSocket events, including nested cache and modality details. `ModelInfoCatalog::responses_ws_token_cost_by_tier` prices each billable WebSocket tier separately. `ModelInfoCatalog::handle_realtime_stream_cost_calculation` selects the first priced session model and adds completed transcription charges. `ModelInfoCatalog::handle_realtime_transcription_cost_calculation` prices those events by duration or audio, text, and output tokens. WebSocket response-level margins, tool charges, and provider-stated costs remain outside this tier calculation

`tiered_pricing::select_tier_for_input` chooses one rate tier for all tokens in a request with an inclusive upper bound and last-tier fallback. `tiered_pricing::tier_rate` reads numeric or YAML string rates, preserving an explicit zero ahead of a fallback

`gemini_cost` prices search and Maps grounding with per-query or per-prompt billing, a configured price or the Python fallback, and server-tool usage fallback for search counts. Gemini's token-pricing wrapper still depends on the broader Python generic token calculator

`vertex_cost` routes Vertex calls by model and call type, prices token usage with Python's above-128k selection, and prices character usage with per-side token fallback. `ModelInfoCatalog::vertex_cost` exposes the call-type route while `cost_per_token` uses the Vertex token wrapper. Both apply the regional endpoint uplift where Python does. The current Python character wrapper uses completion tokens with its above-128k character rate; Rust preserves that behavior

`generic_usage` parses prompt and completion token details for the shared token calculator, including cached modality splits, cache-write aliases, non-token usage counts, and nested reasoning tokens

`generic_input` prices the parsed prompt details with caller-supplied base token rates and model-specific audio, image, video, character, query, count, and duration rates. It preserves Python's service-tier fallback and suppresses token charges when a corresponding image-count or media-duration charge applies. Selecting base rates from full model metadata remains separate

`generic_output` prices text, reasoning, audio, image, and video output tokens and resolves the standard or service-tier reasoning rate. `generic_cost::calculate_generic_cost_with_resolved_rates` joins both sides, adjusts overlapping prompt cache and modality counts, and applies a caller-supplied multiplier. `base_rate_selection` selects flat, service-tier, above-threshold, tier-table, and off-peak rates from model metadata. `calculate_generic_cost_from_model_info_with_region` also selects data-residency, Vertex endpoint, and provider-specific geo multipliers from model metadata and normalized usage at a caller-supplied timestamp

`custom_pricing::normalize_cache_usage` applies Python's cache field precedence and adjusts prompt tokens when cache counts use the Anthropic convention. `custom_pricing::cost_per_token_custom_pricing_helper` prices normalized usage with caller-supplied token or per-second rates. `ModelInfoCatalog::cost_per_token_with_custom` and `cost_per_token_for_call_with_custom` apply those rates before catalog lookup or call dispatch. The module validates finite nonnegative quantities and rates before calculation

`catalog::CostCatalog` accepts a caller-supplied map of model keys to flat token rates. `catalog::ModelInfoCatalog` accepts full model metadata and applies per-second rates for eligible modes or cache, service-tier, threshold, off-peak, and regional token pricing to normalized usage. Wall-clock pricing precedes provider-reported totals as in Python. Both use the same model-key selection order as Python's `cost_per_token`, including duplicate provider prefixes and regional keys. Catalog loading and most specialized provider dispatch remain outside these methods

`ModelInfoCatalog::cost_per_token_for_call` joins the ported token, Vertex character, Together embedding, Azure AI router, speech, transcription, rerank, vector-search, search, OCR, and batch paths behind a typed `CostCall`. It uses Python's call-type order where these paths overlap. The caller supplies OCR response data and optional deployment prices

Response-level search pricing returns after discount and margin, without adding built-in tool charges or caller-supplied additional charges, matching Python's early return

`responses_usage::transform_response_api_usage_to_chat_usage` converts Responses API and realtime token details into chat-shaped usage, including cache-write aliases, cached modality splits, reasoning text partitioning, and provider extras. `anthropic_usage::transform_anthropic_usage_to_chat_usage` handles Anthropic's cache-excluding input tokens, iteration cache splits, and reported thinking tokens. `interactions_usage::transform_interactions_usage_object` handles Interactions modality, cache, tool-use, and reasoning counts. `transcription_usage::transform_transcription_usage_object` maps tagged transcription token usage and drops duration usage. `usage_dispatch::get_usage_object` selects these formats or chat-shaped conversion. `ChatUsage::token_usage` feeds normalized token counts and cache-write splits into the generic Rust calculator. Rust needs the serialized transcription `type` tag because it cannot inspect Python class identity

`model_selection` applies Python's request, base-model, response-model, router-price, provider-prefix, and regional-alias precedence to a caller-supplied catalog. The caller supplies known provider names because this standalone crate does not import Python's provider registry

`model_selection::get_provider_for_cost_calc` uses an explicit provider, a known model prefix, or catalog provider metadata. `completion_cost_from_response` infers it from ordered model candidates before provider-specific pricing, including when the first candidate has no price

`ModelInfoCatalog::pricing_entry_for_cost_calc` returns the catalog key and model metadata used for cost reporting. Explicit deployment pricing comes first, followed by the selected, response, and requested models

`zero_cost_diagnostic` identifies missing rates, priced entries that returned zero, and failed calculations from the selected pricing entry and response usage. It also formats the diagnostic warning and counter reason used by Python logging

`zero_cost_finding` joins response usage and catalog entry lookup, then suppresses findings for cache hits, nonzero charges, and unbilled read or management calls. Background response cost polls remain billable

`background_cost_polling` mirrors the pure background interaction status gates and capped poll intervals. Python still owns fetching, settlement, logging, and budget reservation release

`completion_input` prepares serialized responses for pricing. It selects the response kind's call type, model candidates, normalized usage, and the billable service tier from the request, response, usage, or provider traffic type. The caller supplies the response kind because JSON does not preserve Python class identity

`completion_response::completion_cost_from_response` joins preparation, ordered model fallback, the existing call dispatcher, built-in tool and additional charges, discount, and margin for supported call types. A caller can provide a built-in tool charge or tool settings for calculation from the serialized response and selected model. Token calls use response usage, caller-supplied usage, or a loaded Rust token counter with prompt, messages, and completion text. Explicit custom token and per-second rates take precedence over catalog prices, including for unregistered models. Search, rerank, transcription, and OCR can use response fields without token usage. Image, video, and realtime stream responses return their dedicated costs before discount and margin, as in Python. Responses WebSocket turns use returned service-tier prices and apply fixed margins once per tier. A2A and MCP calls use caller-supplied logging details without catalog prices

For responses with usage, `PricedCompletionResponse::token_breakdown` carries cache-read, cache-creation, and reasoning charges with the billed token rates. Calls without response usage and early-return media, realtime, A2A, MCP, and Replicate paths have no token breakdown

Unregistered Replicate responses use Python's time-based fallback and return before discount and margin. The caller can supply its per-second rate; the crate otherwise uses Python's current default. Serialized `created` and `ended` fields provide the duration fallback when no response time is supplied

Full provider-specific `cost_per_token` routing and several call-type branches of `completion_cost` remain outside Rust. The ported Rust cases use `rstest` and synthetic prices; they cover mapped Python calculations, not integration with Python model registration

The caller states whether `prompt_tokens` includes cache tokens. Threshold selection uses total input tokens for either convention and selects one rate for the whole request. Thresholds are sorted when compiled, and duplicate thresholds or tier overrides fail deterministically. `Fast` selects priority rates; unknown tiers use standard rates

`Rate::Missing`, `Rate::Null`, and `Rate::Value(0.0)` remain distinct. Missing cache rates fall back to the selected input rate, and an absent one-hour write rate falls back to the selected write rate. Missing input or output rates return typed errors, including for zero usage. Python's sparse-entry behavior remains outside this native contract

The model-info off-peak path supports UTC windows, wrapping windows, and weekday rules with an IANA timezone. The lower-level compiled pricing plan still supports one non-wrapping UTC daily window. The caller supplies the provider-specific threshold policy. Negative or non-finite rates, ambiguous rules, inconsistent cache counts, incomplete write splits, invalid plan windows and overflow return errors. Callers must decline unsupported inputs before native execution if their public contract accepts those shapes

This crate accepts a caller-supplied catalog and only supports part of Python's model selection and response normalization. It does not fetch provider prices or cover every provider-stated cost shape. The non-token functions accept already selected prices and do not yet match every Python fallback or warning. This crate does not change proxy behavior. The reference fixture was generated by `tests/generate_python_reference.py` against the Python implementation at the commit recorded in `tests/python_reference.tsv`, using synthetic rates and fixed usage
